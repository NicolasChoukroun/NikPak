1 引言

nikpak 是一个用于 .nik 格式的命令行压缩工具。它的设计围绕四个理念：比现有工具压缩得更好、更快，用现代密码学保护数据，并以单个小型可执行文件在 Windows、macOS 和 Linux 上原样运行。

1.1 设计目标

  • 小。在人们大量实际归档的数据上击败 RAR 7。音频、图像和跟踪器音乐通过内容检测，并用专门的无损编解码器压缩；其余所有数据则使用调优过的多线程 Zstandard 流。
  • 快。压缩和解压应受磁盘限制，而非 CPU。在其快速级别 -m2 下，nikpak 在单核上不到一秒即可压缩约 200 MB 的源文件。
  • 安全。带内存困难密钥派生函数的认证加密，文件名始终隐藏，篡改始终可检测，解压器不会被诱骗把文件写到目标文件夹之外。
  • 抗量子。仅使用 256 位对称密码学。nikpak 中没有任何 RSA、椭圆曲线或 Diffie-Hellman 代码，因此 Shor 算法无物可破。
  • 可移植、可脚本化。单个静态链接的可执行文件、与 RAR 兼容的命令行、可预测的退出码，以及记录每个选项的 -help。

1.3 它是为谁准备的？

nikpak 面向需要大量归档媒体或源代码并关注大小和速度的人，面向需要可脚本化压缩工具（有合理退出码和文档化格式）的开发者，也面向任何需要强加密而又不想信任闭源实现的人。由于命令行遵循 RAR 约定，Total Commander 等前端程序几乎无需重新配置即可驱动它。

3.3 密码详解

当使用 -p 创建压缩包时，nikpak 按以下顺序解析密码，并且绝不会仅仅因为没有提供密码而失败：

  • 命令行上的 -p 或 -P ：按原样使用（最少 8 个字符）。
  • 环境变量 NIKPAK_PASSWORD，可让密码不出现在进程列表中。
  • 交互式提示，询问两次以确认。空输入会生成随机密码。
  • 没有终端时（例如在 GUI 内部），密码通过 stdin 管道传入；如果没有，则生成随机密码。

生成的密码有 24 个字符，来自 56 个无歧义符号的字母表（不含 0/O、1/l/I），约 139 位熵。它在控制台上以方框形式打印一次。没有恢复途径：丢失密码的压缩包任何人都无法打开。

打开加密压缩包时，nikpak 使用同样的来源，然后用退出码 11 和说明性消息失败；它从不生成任何东西，因为生成的密码不可能匹配。

nikpak a -m5 -mt8 big.nik Projects\ # maximum, 8 threads

nikpak x backup.nik C:\Restore\ # extract with paths
nikpak e backup.nik *.jpg C:\Pics\ # only *.jpg, flat
nikpak x backup.nik Docs/report.pdf # extract ONE file
nikpak e backup.nik Docs/report.pdf -d C:\Out # one file, no path
nikpak x backup.nik Photos -d C:\Restore # one folder
nikpak l backup.nik *.pdf # list only PDFs
nikpak p backup.nik notes.txt # show a file
nikpak d backup.nik Temp *.bak # delete entries
nikpak l backup.nik # list
nikpak t secret.nik # test (asks password)
nikpak mt song.wav tracker.mod photo.bmp # which filter wins?



3.6 与 Total Commander 及其他前端的集成

由于 nikpak 接受 RAR 的命令语法（a、x、e、l、t、@listfile、-p、-ep1、-o+、-y、-m），能够驱动外部 rar.exe 的程序也能驱动 nikpak.exe。在 Total Commander 中，在配置、压缩器、附加压缩程序下注册扩展名 nik，并将压缩和解压命令指向 nikpak.exe。无人值守解压时使用 -o+ 或 -y，因为没有控制台时 nikpak 无法询问是否覆盖，而是会跳过已有文件。菜单名称因 Total Commander 版本而异；请查阅其内置帮助了解具体字段。

Windows 上带空格的文件夹
以反斜杠结尾的加引号路径（如 "C:\My Folder\"）会被 Windows 错误解析（末尾的引号被视为转义）。对于带空格的目标位置，请改用 -d "C:\My Folder"。



3.7 图形界面

nikpak 不带参数启动时（例如双击 nikpak.exe），会打开一个小窗口而不是打印用法。它只做一件事：压缩你拖到它上面的内容。

  • 拖入文件或文件夹，或一次拖入多个，放在窗口上；或点击圆圈（或 choose files / choose a folder 链接）在对话框中选择；点击圆圈会在环内显示 Choose files 和 Choose a folder 两个按钮。它们以最佳压缩（-m5）压缩到一个压缩包中，以文件（去掉扩展名）、文件夹命名；若有多个项目，则以它们所在的文件夹命名。已有压缩包绝不会被覆盖：report.nik 变为 report (2).nik。
  • 进度以环形仪表中的大百分比显示，并带阶段（分析中、压缩中、收尾中）、已处理数量和耗时。其下方的 Cancel 按钮（或 Esc 键）会立即停止长时间压缩并删除未完成的压缩包；窗口保持打开以备下一次。压缩过程中关闭窗口效果相同。
  • 完成：环变为绿色，显示压缩包名称、其与原始大小的对比和耗时。Show in folder 在 Explorer、Finder 或文件管理器中打开它；Compress more（或点击圆圈）开始下一个。
  • 保存到：底部的目标文件夹可以输入或用 Browse 选择。下次会记住（Windows：%APPDATA%\nikpak\settings.txt；macOS：~/Library/Application Support/nikpak；Linux：~/.config/nikpak）。首次为桌面。
  • 社区：右下角的三个圆形按钮打开 nikpak 的 Telegram、X 和 Discord 页面（第 1.5 节）。
  • 切换到 unNik：i 按钮左侧带向上箭头的圆形按钮会关闭 NikPak 并启动 unNik（第 3.9 节）。压缩完成后，它以及完成屏幕上的 Open in unNik 链接会立即打开新压缩包。压缩进行中该按钮被禁用。
  • 打开目标文件夹：Save to 字段和 Browse 之间的文件夹按钮会在 Explorer 或 Finder 中打开该文件夹；压缩完成后，打开时新压缩包处于选中状态。
  • 声音：按钮、链接和选项有轻柔的点击声，每个动作（开始工作、成功、错误、取消、切换程序、文件悬停在窗口上）有短促的提示音。它们由程序本身生成，没有声音文件。标题栏的扬声器按钮可关闭和开启声音；默认开启，且此选择与 unNik 共享。

4 架构

nikpak 是单个 Rust 程序，约 9,600 行（含单元测试），分布在十六个源文件中，外加私有许可证工具 nikpak-keygen。其核心设计规则是流式：文件以 256 KiB 块读取，推过一串写入器，从不整体保存在内存中（唯一的例外是 BMP 像素数据，限制为 256 MiB，以及编解码器的 64 KiB 工作缓冲区）。

4.3 逐步创建压缩包

  • 验证输出位置。已有压缩包仅在使用 -o+（或交互式确认）时被替换；否则 nikpak 会说明不支持追加。
  • 收集输入：展开通配符（PowerShell 不会这样做）、读取 @listfiles、应用排除、跳过符号链接和特殊文件并给出警告，且压缩包绝不会添加到自身。
  • 若请求了加密，则解析密码（第 3.3 节）并用 Argon2id 派生密钥。
  • 写入文件头，然后构建写入器链：文件、缓冲写入器、可选的分块加密器、Zstandard 编码器。
  • 写入每个条目。媒体文件经过检测和试算（第 7 章）；其他一切以 256 KiB 块复制，同时计算 CRC32。
  • 写入结束标记（含条目计数），完成 Zstandard 帧，密封最后一个加密分块并刷写到磁盘。
  • 重命名 name.nik.tmp 为 name.nik。若此前任何步骤失败，守护对象会删除临时文件，因此半写入的压缩包绝不会替换完好的压缩包。

4.4 逐步解压压缩包

  • 读取并验证文件头：魔数、版本、标志、方法，以及（加密压缩包）Argon2id 参数，后者在任何内存分配之前先做范围检查。
  • 获取密码并派生密钥。第一个认证分块随后证明或否定该密码。
  • 遍历条目流。每个条目名称在任何文件系统访问之前先经过清理（第 10.1 节）。
  • 用 create_new 写入文件，设置时间戳和权限，并验证重建字节的 CRC32。CRC 失败的文件会被删除而不是保留。
  • 验证压缩包结尾：结束标记之后流必须真正结束，且（若加密）最后一个认证分块必须已被处理。这可捕获截断和追加的数据。

4.5 内存与线程

Zstandard 用工作线程压缩（默认全部内核，用 -mt 限制）。解压、音频编解码器和加密在调用线程上运行。Argon2id 密钥派生需要 64 MiB，最高两个级别使用 128 MiB 匹配窗口，因此解压此类压缩包最多需要这么多内存。

5 .nik 容器格式

.nik 文件是一个小的固定文件头，后跟主体。主体是一条固实流：所有条目串接在一起，一起压缩，并可选择加密。格式第 2 版增加媒体记录；第 1 版压缩包仍可读取。

5.3 加密主体分帧

设置加密标志时，zstd 输出被切成 64 KiB 明文的块。每个块存储为 32 位大端长度后跟密文，因 Poly1305 标签而长 16 字节。块只有在后面至少还有一个字节时才密封，因此最后一个块永远不会为空，并可标记为最终块（第 8.3 节）。

5.4 为什么是固实流？

把所有文件压缩为一条流能让压缩器发现文件之间的重复，这对源代码树和文档集合极为重要（第 11 章的基准测试显示，在 10,949 个文件上 RAR 的非固实输出几乎是其固实输出的两倍大）。代价是顺序访问：解压单个文件需要解压它前面的内容。nikpak 通过跳过媒体条目而不解码来降低这一成本。

5.5 版本化

版本字节会对照程序理解的最新版本检查。较新的压缩包会产生消息 Unsupported archive version N; please update nikpak，而不是误导性的损坏错误。未知的标志、方法或媒体过滤器也以同样方式拒绝。

5.6 多引擎主体（版本 3）

用 -m5 制作的压缩包使用方法 2。5.2 中描述的内部记录流不变，但它只在条目之间被切成块，每个块用自己的引擎压缩。串接起来后，解压出的块恰好是单引擎压缩包的记录流，因此列出、测试和解压以相同方式工作。

6 压缩引擎

6.1 为什么选择 Zstandard

Zstandard 将 LZ77 匹配与由 Huffman 编码和有限状态熵（FSE）构建的熵编码阶段相结合。与 ZIP 的 Deflate 算法相比，它能在远更大的窗口上找到匹配，用更紧凑的熵码对字面量和匹配长度建模，并以每秒数 GB 的速度解码。它还是一个开放、被广泛审计的格式，使 nikpak 的数据能被独立工具恢复。

6.2 级别映射

nikpak 接受 RAR 风格级别（-m0 .. -m5）和 zip 风格级别（-0 .. -9），并将它们映射到 Zstandard 级别：

选项Zstandard 级别特点
-m0无（存储）无压缩、无媒体过滤器
-m1 1最快
-m2 3快速；单核上 197 MB 约 0.9 秒（1.2.0 之前的默认值）
-m3 9良好平衡
-m4 15高；128 MiB 窗口和长距离匹配；Deflate 再压缩（7.9）
-m5 (default)LZMA2 / PPMd最高，且自 1.2.1 起为默认：多引擎主体（6.7）和 Deflate 再压缩



zip 风格级别映射如下：-0 存储，-1 到 -6 使用 Zstandard 1 到 6，-7 使用 9，-8 使用 12，-9 与 -m5 相同。

6.3 大窗口与长距离匹配

在 Zstandard 级别 15 及以上，nikpak 启用 2^27 字节（128 MiB）匹配窗口和长距离匹配。源代码树、文档集和备份包含许多在流中相距很远的近似重复文件；普通 8 MiB 窗口无法看到它们之间。在 197 MB 测试集上，这使 -m5 的输出从 26.3 MB 降至 24.4 MB，-m4 从 29.5 MB 降至 26.8 MB，-m4 的速度无损失，-m5 略有损失。2^27 的窗口在 Zstandard 默认解码器限制之内，因此任何标准解码器都能读取这些数据。

6.4 多线程

编码器把输入分成在（默认全部内核的）工作线程上运行的作业。因此压缩速度随内核数量扩展，而格式仍为单条流。本指南中的所有数字都在单核上测量；在典型多核机器上，nikpak 比所示快得多。

6.5 流内的完整性

Zstandard 帧携带自身的内容校验和，nikpak 为每个文件增加 CRC32 和带条目计数的结束标记。因此，损坏的未加密压缩包在三个层面被检测：帧校验和、每文件 CRC 和结束标记。

6.6 存储模式

-m0 不加压缩地写入条目。它对已经压缩过的数据有用，也是唯一有意绕过媒体过滤器的模式：要求存储的用户并不希望数据被变换。

6.7 最高级别：LZMA2 和 PPMd

Zstandard 是速度的正确引擎，但在其最强设置下，源代码和文档仍比 LZMA2 落后几个百分点，在散文上远落后于 PPMd。因此自 1.2 版起，-m5 用两个块构建压缩包（格式见 5.6）：

  • 二进制块。文件夹、二进制文件、媒体条目和经 Deflate 再压缩的条目用 LZMA2 压缩：预设 9、nice 长度 273、匹配查找器深度 32，字典大小随数据调整（1 到 128 MiB）。
  • 文本块。前 64 KiB 不含零字节且几乎不含控制字符的文件（源代码、文本、CSV、HTML、XML……）进入第二个块。这些文件连续四个 1 MiB 段分别用 PPMd 变体 I（阶数 8，192 MiB 模型）和为文本调优的 LZMA2（lc 4、pb 0）试压缩，取较小者。散文偏向 PPMd；含有大量近似相同文件的大源代码树偏向 LZMA2，因为它能跨文件复制长重复。
  • 顺序。在每个块内，文件按扩展名排序，再按文件名排序，如同 7-Zip，使相同或相似的文件相邻。连同连续试算样本，这使通用数据集缩小 7.5 %。

"Extreme" LZMA2 设置经过测量后被否决：在电子表格 XML 上它们慢达十倍且并不更小。-m5 在单线程上运行，无论 -mt 如何。

7 媒体智能

通用压缩器看到的是字节。它不知道 WAV 文件是波形，其下一个采样可由前几个预测，也不知道照片的相邻像素几乎相等。nikpak 的媒体层提供这一知识：它识别此类文件，应用揭示冗余的无损变换，并让压缩器（或专用编解码器）利用它。这正是 nikpak 相对 RAR 获得最大优势之处。

7.3 NAC 音频编解码器

NAC（nikpak 音频编解码器）是用于整数 PCM 的基于块的无损编解码器。它与 FLAC 同族：线性预测后跟 Rice 编码。它有自己专为本压缩包设计的位流，用于 WAV、AIFF 和 MOD 文件的采样数据。

块与立体声去相关

音频被切成 4096 采样帧的块，每块独立编码，这使编解码器稳健（错误不会扩散），并让编码器适应变化的素材。对于立体声，编码器在每个块从四种表示中选择一种：

模式编码的声道重建
0左、右直接
1左、边 R = L - S
2边、右 L = R + S
3中、边sum = (M << 1) | (S & 1), L = (sum + S) >> 1, R = (sum - S) >> 1



其中 Side = L - R、Mid = (L + R) >> 1。边声道比普通声道需要多一位，以 bits + 1 编码。模式选择很廉价：编码器对 L、R、M 和 S 的 2 阶固定预测器残差绝对值求和，取总和最小的一对。对于声道强相关的录音，中/边通常能节省几个百分点。

固定预测器

order 0: e[i] = x[i]
order 1: e[i] = x[i] - x[i-1]

order 3: e[i] = x[i] - 3*x[i-1] + 3*x[i-2] - x[i-3]
order 4: e[i] = x[i] - 4*x[i-1] + 6*x[i-2] - 4*x[i-3] + x[i-4]



块的前 order 个采样按原样存储为预热值。

线性预测编码（LPC）

对于有调性和和声的音乐，系数拟合到块的预测器远优于固定多项式。编码器按如下步骤计算它们：

  • 对块应用 Tukey 窗（在首尾四分之一处渐隐），使边缘不扭曲统计量。
  • 计算加窗信号的自相关 r[0..32]。
  • 运行 Levinson-Durbin 递归，它一次遍历即给出 1 到 32 每个阶数的最优系数集：k = (r[i] - sum a[j] r[i-j]) / err、a[i] = k、a[j] = a[j] - k a[i-j]、err = err (1 - k^2)。
  • 把实系数量化为整数，精度 12、14 或 15 位（取决于采样位宽），选择 2 的幂标度（shift，0 到 20），使最大系数刚好放得下。舍入使用误差反馈，因此量化误差不会跨系数累积。
  • 评估若干阶数（集合取决于努力级别，见下），计算每个的残差，保留估计总大小最小者（包括发送其系数的成本）。

预测器本身是纯整数运算，这正是解码器运行的：

pred[i] = (q[0]*x[i-1] + q[1]*x[i-2] + ... + q[n-1]*x[i-n]) >> shift
e[i] = x[i] - pred[i] (n = order; the sum uses 64 bits)



浮点仅由编码器用于决定发送哪些整数系数。解码器从不接触浮点，因此解码在每个处理器和每个编译器上都逐位精确。

残差编码

预测误差用 zig-zag 变换（u = (e << 1) XOR (e >> 63)，使小的正负值变成小的数）映射为无符号数，并用分区 Rice 编码编码。块的残差分成 2^p 个分区（p 从 0 到 8，由编码器选择）；每个分区有自己的 Rice 参数 k（5 位）。一个值写为 u >> k 的一元表示（那么多零后跟一个一）加低 k 位。分区的最佳 k 由其值之和推导，因此每个候选预测器的成本可从运行和廉价估计，而无需实际编码。

努力级别

压缩包的级别（-m 选项）选择每个块尝试多少 LPC 阶数。阶数更多意味着结果略小、编码器更慢；解码器速度相同。

7.4 自验证

写入压缩包是检测编码器错误的唯一机会，因此 NAC 编码器不信任自己。编码每个块后，它会再次解码该块并与原始采样比较。任何差异时，它把该块重新编码为原样（不会失败）并再次检查；如果连这也失败，压缩停止，给出明确错误并建议使用 -mc-。后备路径由单元测试覆盖，它们对位深和声道数的每种组合强制原样编码；该机制把可能的静默数据丢失错误变成可检测、可恢复的状况。

此外，解码器经过模糊测试：单元测试向其输入数千个随机字节块和翻转位的块，它必须返回错误而不 panic 或分配不合理的内存。开发期间这发现了一个真实错误（对 32 位素材，Rice 参数搜索可能结果为空，并回退到一个会产生数 GB 码的参数）；已修复并有测试覆盖。

7.5 Shuffle 和 Shuffle+Delta

有些音频对预测没有反应。基准测试使用的画廊 WAV 文件是 16 位，却只包含约一千个不同的采样值，因为它们由 8 位压扩源产生。预测器无法利用这一点，FLAC 把它们压缩到原始的 84 %，而普通 Zstandard 需要 63 %。有帮助的是排列字节，使压缩器看到同质数据：

  • Shuffle 把采样的字节分成平面：先是声道 0 的所有最低有效字节，再是声道 0 的所有最高有效字节，然后声道 1，依此类推，以 32768 帧为块。高字节平面平滑，低字节平面字母表非常受限；Zstandard 的熵编码器对两者的建模远好于交织混合。
  • Shuffle+Delta 先把每个采样替换为其与同声道前一个采样的差（按采样位宽取模，因此精确可逆，状态跨块携带），然后洗牌。当信号平滑但不足以让 NAC 胜出时，这有帮助。

在 35 个画廊文件上，按文件选择最佳过滤器（由试算选出）的压缩包在 -m2 为原始大小的 51 %，-m5 为 47 %，而普通 Zstandard 为 63 %。

7.6 ProTracker MOD 文件

MOD 模块是 1084 字节的头（标题、31 个采样描述符、128 项的模式顺序表和偏移 1080 处的 4 字节签名），然后是模式数据，再是所有乐器的原始 8 位有符号采样。nikpak 计算采样从哪里开始以及多长：

patterns = max(order table) + 1
sample_start = 1084 + patterns * 256 * channels (4 ch: 1024 B per pattern)
sample_bytes = sum of (length in words * 2) over the 31 descriptors,
clamped to the end of the file



头和模式原样存储（压缩器能很好处理那些重复音符事件），采样区域作为单声道、有符号 8 位流用于试算。按文件，NAC、Shuffle+Delta 或普通压缩胜出：采样乐器大多偏向 NAC，而某些模块（例如采样非常短或高度重复的）普通压缩胜出。截断的模块通过把区域钳制到实际存在的数据来处理。

7.7 BMP 图像

未压缩的 BMP 存储填充到四字节倍数的像素行。过滤器分四步工作：

  • 拆分像素区域为每个声道一个平面（B、G、R，32 位还有 A），单独记住每行的填充字节。
  • 去相关颜色。从蓝和红平面减去绿平面（模 256）。照片中三个声道强相关，因此差值很小。
  • 用 MED（中值边缘检测）预测器——LOCO-I 图像编码器所用的那个——预测每个像素：对于左 a、上 b 和左上 c，预测为 min(a,b)（若 c >= max(a,b)）、max(a,b)（若 c <= min(a,b)），否则为 a + b - c。预测误差替换像素（模 256）。在边缘上预测器跟随边缘；在平滑梯度上它外推梯度。
  • 串接残差平面和填充字节，让 Zstandard 压缩它们。平滑区域变成近零字节的游程。

解码器精确反向执行这些步骤。8 位 BMP 跳过颜色步骤；试算随后决定预测对该调色板是否有帮助，因为预测调色板索引只对灰度或平滑有序的调色板有意义。256 MiB 以上的 BMP 文件不过滤，以限制内存使用。

7.8 为什么这能胜过 RAR

RAR 用其通用匹配加 Huffman 引擎外加少量字节过滤器压缩媒体。nikpak 则给音频真正的预测编解码器，带逐块立体声去相关和自适应 Rice 编码；给图像真正的二维预测器，带颜色去相关；并按文件测量选择。后果在基准测试中可见：各种音频小 12 到 15 %，跟踪器音乐小 13 %，照片小 39 %，立体声轨道的 NAC 结果与专用 FLAC 编码器相差 0.2 % 以内。

7.9 Office 文档、PDF 和 gzip：Deflate 再压缩

现代 Office 文件是 XML 的 ZIP 压缩包（docx、xlsx、pptx、odt、ods），PDF 文件把页面存储在 Deflate（FlateDecode）流中。因此其内容已经压缩，没有压缩工具能大幅缩小：在 1.1 基准测试中，6.6 MB 的 .xlsx 文件用 7-Zip 只降到 5.6 MB。nikpak 1.2 移除了这一障碍。

  • 按内容检测。文件开头的 ZIP 本地头（PK\x03\x04）、%PDF- 或 gzip 头；从不使用扩展名。
  • 解码。找到每个 Deflate 流（方法 8 的 ZIP 条目、带 zlib 头的 PDF 流、每个 gzip 成员）并用 preflate（微软的 preflate-rs）分析。preflate 返回普通数据外加一个小的修正记录，精确描述原编码器（无论哪个）是如何做出选择的。
  • 存储。文件存储为原始段和（普通数据、修正）对的序列。普通 XML 或页面描述随后进入固实流，LZMA2 把它压缩到其 Deflate 大小的一小部分。
  • 验证。在使用结果之前，nikpak 重建每个 Deflate 流，并把整个文件的长度和 CRC32 与原始比较。若有任何差异，或 preflate 在畸形文件上失败或 panic，文件就简单地按普通方式存储。
  • 解压。Deflate 流逐位重建，因此解压出的 .docx 或 .pdf 逐字节相同，其 CRC32 与每个条目一样被检查。

在第 11.7 节的 Office 集上，这正是 nikpak 比所有其他压缩工具都小的原因。6.6 MB 的 .xlsx 文件解码后含 71 MB XML，而该 XML 的压缩远好于 Deflate。代价是时间：preflate 每秒约分析 15 MB 普通数据。因此再压缩仅在 -m4 和 -m5 使用，那里物有所值（实测：-m3 花六倍时间只多得 0.5 %）。限制：文件最大 512 MiB，每条流最多 512 MiB 普通数据和 64 MiB 修正。-mc- 将其关闭。

8 加密

nikpak 的加密完全由标准的、经过充分研究的组件构建（Argon2id 和 XChaCha20-Poly1305 的 RustCrypto 实现）。没有为本项目发明任何原语；工作在于正确组合它们。

8.1 威胁模型

该设计假设攻击者取得压缩包文件，可从容研究和修改它，并能离线无限次尝试密码猜测。nikpak 旨在保证：

  • 文件内容以及它们的一切相关信息的机密性：名称、大小、时间戳、权限和文件数量。
  • 完整性与真实性：对压缩包的任何更改，无论是对数据、文件头、数据顺序还是其长度，都在错误数据被接受之前被检测。
  • 抗猜测：每次密码猜测都尽可能昂贵。

它不隐藏压缩包存在的事实，也不隐藏其大致大小；它无法防御创建或打开压缩包的机器上的恶意软件，也无法防御弱密码。

8.2 从密码到密钥：Argon2id

密码是糟糕的密钥：短、可预测、由人输入。它用 Argon2id 变成 256 位密钥——密码哈希竞赛的获胜者，也是 RFC 9106 标准化的算法。Argon2id 故意内存困难：计算一个密钥需要一大块内存，先填充，再以数据相关模式反复读取。nikpak 使用该 RFC 的低内存配置：

内存困难正是 Argon2id 与较旧的 PBKDF2（RAR5 和 ZIP 的 AES 模式使用）的区别：PBKDF2 几乎不需要内存，因此显卡或定制芯片可以并行测试海量猜测。用 Argon2id，攻击者的硬件必须为每次并行猜测提供 64 MiB，这消除了大部分优势。合法用户的成本是几分之一秒，每个压缩包付一次。

参数存储在文件头中，因此未来版本可以提高它们而不破坏旧压缩包。读取时，先做范围检查（内存 8 × 通道数 最多 1 GiB，遍数 1 到 64，通道数 1 到 64），这样恶意压缩包无法在密码被检查之前让 nikpak 分配荒谬数量的内存。

8.3 STREAM 构造中的 XChaCha20-Poly1305

主体数据用 XChaCha20-Poly1305 保护，这是一种带关联数据的认证加密（AEAD）密码：ChaCha20 提供 256 位密钥流密码，X 变体把其随机数扩展到 192 位（大到可以随机选择而永不重复），Poly1305 为每条密封消息添加 128 位认证标签。ChaCha20 无需特殊指令在任何 CPU 上都很快，且与基于表的 AES 不同，天然没有缓存时序泄露。

压缩包远大于一条消息，因此 nikpak 使用 STREAM 构造（现代文件加密工具所用的同一种）：数据切成 64 KiB 块，第 i 个块在随机数下密封

nonce (24 bytes) = random prefix (19 bytes)
| chunk counter (4 bytes, big endian)
| last-chunk flag (1 byte)



这同时给出三项保证。每个块都有唯一随机数，这对流密码至关重要。因为计数器是随机数的一部分，重排或复制块会导致认证失败。因为最终块携带不同标志，把压缩包截短，即使恰好截在块边界，也会导致认证失败：新的最后一个块是作为非最终块密封的。19 字节前缀每个压缩包随机。

此外，完整的压缩包头（版本、标志、方法、Argon2id 参数、盐和随机数前缀）作为关联数据传给每个块。它被认证但不加密；翻转其中任何一位都会使每个块失败。这也阻止了试图削弱存储参数的降级攻击。

8.5 密码处理

  • 最小长度。创建压缩包时 8 个字符；更短的密码被拒绝并给出说明。

  • 内存卫生。派生的密钥和密码字符串在不再需要时从内存擦除（zeroize crate）。
  • 通道。命令行（-p）、环境变量 NIKPAK_PASSWORD、交互式提示，或没有终端时的 stdin。命令行形式方便但在进程列表中可见；其他形式更可取。

9 抗量子

量子计算机严重威胁某些密码学，而几乎不影响其他密码学。nikpak 的设计站在几乎不受影响的一边。

9.3 密码怎么办？

密码的密钥空间是 256 位，但密钥由密码派生，因此真实强度是密码熵与 256 位中较小者。面对量子对手，密码熵至多（对攻击者最有利）减半：

结论是熟悉的那个，只是说得更尖锐：弱点是密码，而不是加密算法。使用生成的密码或长随机口令，压缩包即可在可预见的未来抵御经典和量子攻击者。Argon2id 在两个世界都有帮助，因为每次猜测的成本由内存主导，而 Grover 算法并不让内存变便宜。

9.4“先收割，后解密”

经常被引用的量子威胁是，对手今天记录加密数据，等量子计算机出现后再解密。对于用 RSA 或椭圆曲线交换密钥的系统，如 TLS 连接或电子邮件加密，这是真实的。nikpak 压缩包没有密钥交换：其密钥来自一个从不离开用户头脑或密码管理器的秘密。存储的副本以后只能靠猜测该秘密来打开，而量子计算机并没有从根本上让这变得更容易。

9.5 如实的局限与前路

  • “抗量子”意味着没有任何已知量子算法能对这些原语胜过通用搜索。这不是证明；对 ChaCha20 和 Argon2 的密码分析仍在继续，且格式已版本化，因此参数或算法可以更改。
  • 如果将来加入公钥共享（把压缩包加密给接收方的密钥），将使用混合方案，X25519 与 ML-KEM 结合，这样任一组件成立即安全。
  • 抗量子不能防止实现错误。见第 8.6 和 10 节。

10 加固与健壮性

压缩工具读取陌生人写的文件，并在用户磁盘上写文件，这使它成为典型目标。nikpak 把每个压缩包都当作不可信输入。

10.1 安全解压

  • 路径穿越（“zip slip”）。每个条目名称被规范化：反斜杠变斜杠，空的和 . 组成部分被丢弃，任何 .. 组成部分导致该条目被跳过并警告。绝对名称失去其根，因此 /etc/passwd 被解压到目标文件夹内部。
  • Windows 名称。在 Windows 上运行时，包含 < > : " | ? * 或控制字符、以空格或点结尾、或等于保留设备名（CON、PRN、AUX、NUL、COM1-9、LPT1-9）的组成部分被拒绝。
  • 符号链接。写入前，检查目标路径在目标文件夹之下的每个已有组成部分；链接从不被跟随。已有文件先删除，新文件用 create_new 创建，它拒绝打开已有路径，因此链接无法用于重定向写入。
  • 特权位。setuid、setgid 和 sticky 位从不恢复；权限被掩码到普通 rwx 位。
  • 失败的文件。CRC32 不匹配的文件被删除，不留残余。

在测试中解压了一个手工构建的压缩包，内含 ../../evil.txt、/tmp/evil.txt、..\..\evil.txt 和 ok/../../evil.txt：没有任何东西逃出目标文件夹，不安全条目被报告并跳过，目标文件夹中植入的符号链接被拒绝。

10.2 有界解码器

  • Argon2id 参数在任何分配之前做范围检查（第 8.2 节）。
  • 加密块的长度必须在 16 字节到 64 KiB + 16 之间；名称最多 4096 字节；音频块必须声明合理的长度；BMP 区域限制为 256 MiB；一元 Rice 编码有上限。
  • 音频和媒体解码器在单元测试中被输入数千个随机和位翻转的输入，必须返回错误，从不 panic 或中止。
  • nikpak 自己的代码不含 unsafe 块，Rust 的边界检查把在 C 中会是内存损坏错误的任何逻辑错误变成干净失败。

nikpak 不限制压缩包的扩展比，因此与每个压缩工具一样，精心构造的“压缩炸弹”解压时可以填满磁盘。如果这很重要，先用 t 测试未知压缩包。

10.3 安全创建与如实的错误

  • 压缩包写入 name.nik.tmp，完成后才重命名；任何失败时守护对象删除临时文件，因此中断的运行绝不会留下半写入或被替换的压缩包。
  • 如果文件在被压缩期间变短，nikpak 用明确消息中止，而不是写入不一致的条目。不可读文件、符号链接和特殊文件被跳过并警告（退出码 1），压缩包绝不会添加到自身。
  • 错误被分类，以便脚本响应：压缩包内的校验和或帧错误是损坏（退出码 3），认证失败是密码错误或篡改（退出码 11），被拒绝的写入是致命错误（退出码 2）。

12.3 抗量子纵观

nikpak 和 RAR5 都用 256 位对称密钥加密，因此两者都不受 Shor 算法影响，都对 Grover 保持约 128 位安全性。任一说法都无法区分二者。nikpak 在其上加的是内存困难的密码步骤（使主导的现实攻击——密码猜测——昂贵得多）和认证加密（使篡改可检测）。它也从一开始就在假设没有任何公钥原语会成为压缩包格式一部分的前提下设计，其路线图承诺若加入公钥共享则采用混合后量子方案。

12.4 该选哪个

  • 选择 nikpak 用于大小和速度都重要的音频、图像、跟踪器音乐和源代码压缩包，用于脚本化备份，用于强大的默认加密，以及当开放、文档化的格式有价值时。
  • 选择 RAR 当你需要恢复记录、分卷或自解压压缩包、原地更新，或必须与只有 RAR 工具的人交换压缩包时。
  • 两者都用：没有什么阻止工作流用 nikpak 处理批量媒体和加密备份，同时保留 RAR 用于分发。

12.5 那 7-Zip 和 ZIP 呢？

第 11.7 节也测量 nikpak 1.2 对 7-Zip 23.01 和 Info-ZIP 3.0。简而言之：

  • 选择 nikpak -m5 获得最小的压缩包。它在所测每个集合上比 7-Zip -mx9 小 2.4 到 31.7 %：Office 文件 31.7 %，文本 15.9 %，源代码 2.4 %。选择 nikpak -m2 用于快速备份（源代码上比 7-Zip 默认快 56 倍）。nikpak 还有更强的加密：7-Zip 用 AES-256，其 SHA-256 密钥派生不内存困难，且它只用 -mhe 隐藏文件名。
  • 选择 7-Zip 当最高级别时间更重要时（它在大型 Office 和源代码集上更快），当你需要其默认级别在文档上就很小，或当你需要打开 7-Zip 可读的众多格式时。
  • 选择 ZIP 只为兼容。每个操作系统无需额外软件即可打开它，但 nikpak -m5 小 19.9 到 60.4 %，且 ZIP 的传统加密很弱。

nikpak 用 Rust 编写，用 Cargo 构建。在 Windows 上，Rust 需要一个来自 Visual Studio Build Tools 的 C/C++ 链接器。在管理员 PowerShell 中，一次性安装两者，然后重新打开 PowerShell：

如果 winget 不可用，从 rustup.rs 安装 Rust，并安装带使用 C++ 的桌面开发工作负载的Visual Studio 生成工具。然后，在包含源代码的文件夹中：

.\build.ps1 -Test # runs the unit tests first

build.ps1 检查 Cargo 是否已安装（若没有则说明如何安装），运行构建，失败时解释常见原因，并把可执行文件复制到 dist\nikpak.exe。

Windows 安装程序

Rust 项目不使用 npm，因此从不要求 npm。为方便起见，项目包含一个小 package.json，其脚本只是调用 Cargo，因此生活在 Node.js 工作流中的开发者可以输入熟悉的命令：

13.3 自包含可执行文件

文件 .cargo/config.toml 为 Windows MSVC 目标静态链接 C 运行库。因此生成的 nikpak.exe（带图形界面几 MB，无界面约 2.3 MB）没有 DLL 依赖，在运行它的机器上不需要Visual C++ 可再发行组件。把它复制到 PATH 上的文件夹即可在任何地方使用。发布配置启用完全优化、链接时优化、单一代码生成单元、符号剥离和 panic = abort，以获得小而快的二进制文件。

$archive = "D:\Backups\docs-$(Get-Date -Format yyyy-MM-dd).nik"

$env:NIKPAK_PASSWORD = Get-Content "$env:USERPROFILE\.nikpak-secret"


nikpak a -p -m3 -inul $archive "$env:USERPROFILE\Documents"
if ($LASTEXITCODE -gt 1) { throw "nikpak failed: $LASTEXITCODE" }

if ($LASTEXITCODE -ne 0) { throw "archive verification failed" }

export NIKPAK_PASSWORD="$(cat ~/.nikpak-secret)"
