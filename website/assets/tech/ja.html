1 はじめに

nikpak は .nik 形式のコマンドラインアーカイバです。設計の出発点は四つあります。既存のツールより小さく圧縮すること、より高速に処理すること、現代的な暗号技術でデータを保護すること、そして単一の小さな実行ファイルとして Windows、macOS、Linux でそのまま動作することです。

1.1 設計目標

  • コンパクト。 実際に大量にアーカイブされるデータで RAR 7 を上回ること。音声、画像、トラッカーミュージックは内容から判別され、専用の可逆コーデックで圧縮されます。それ以外は調整済みのマルチスレッド Zstandard ストリームで処理されます。
  • 高速。 圧縮と展開は CPU ではなくディスクによって制限されるべきです。高速レベル -m2 では、nikpak は 1 コアで約 200 MB のソースファイルを 1 秒未満でアーカイブします。
  • 安全。 メモリハードな鍵導出関数を用いた認証付き暗号、常に隠されるファイル名、常に検出される改ざん、そして宛先フォルダーの外へ書き込むよう欺くことができない展開ツール。
  • 耐量子。 使用されるのは 256 ビットの対称暗号だけです。nikpak のどこにも RSA、楕円曲線、Diffie-Hellman のコードはないため、Shor のアルゴリズムが破るものは何もありません。
  • ポータブルでスクリプト化可能。 静的にリンクされた 1 つの実行ファイル、RAR 互換のコマンドライン、予測可能な終了コード、そしてすべてのオプションを記載した -help。

1.3 対象読者

nikpak は、大量のメディアやソースコードをアーカイブし、サイズと速度を重視する人、スクリプトから扱えて妥当な終了コードと文書化された形式を備えたアーカイバを求める開発者、そしてクローズドな実装を信頼せずに強力な暗号化を必要とするすべての人を対象としています。コマンドラインは RAR の慣習に従っているため、Total Commander などのフロントエンドからほとんど、あるいはまったく再設定なしで操作できます。

3 コマンドラインリファレンス

nikpak は RAR ユーザーに馴染みのある構文に従います: nikpak [options] [files...]。オプションはアーカイブ名の前でも後でも指定でき、-- でオプション解析を終了します。

3.1 コマンド

コマンド意味

xフルパスで展開します。すべて、またはアーカイブ名の後に指定した名前・フォルダー・ワイルドカードのみ (nikpak x backup.nik Docs/report.pdf は 1 ファイルを展開します)。末尾のパス区切り (または -d dir) が保存先を指定します。

3.3 パスワードの詳細

-p を付けてアーカイブを作成するとき、nikpak は次の順序でパスワードを解決し、パスワードが指定されなかったというだけで失敗することはありません。

  • コマンドラインの -p または -P : そのまま使用されます (最小 8 文字)。
  • 環境変数 NIKPAK_PASSWORD。パスワードがプロセス一覧に現れないようにします。
  • 対話プロンプト。確認のため 2 回尋ねられます。空の入力ではランダムパスワードが生成されます。
  • ターミナルがない場合 (たとえば GUI 内)、標準入力からパイプされたパスワード。ない場合はランダムパスワードが生成されます。

生成されるパスワードは、紛らわしい文字を含まない 56 文字のアルファベット (0/O、1/l/I を除く) からなる 24 文字で、約 139 ビットのエントロピーを持ちます。コンソールのボックスに一度だけ表示されます。復元はできません: パスワードを失ったアーカイブは誰も開けません。

暗号化アーカイブを開くとき、nikpak は同じ情報源を使用し、失敗した場合は終了コード 11 と説明メッセージを返します。生成されたパスワードは一致し得ないため、何も生成しません。

3.6 Total Commander およびその他のフロントエンドとの統合

nikpak は RAR のコマンド構文 (a、x、e、l、t、@listfile、-p、-ep1、-o+、-y、-m) を受け付けるため、外部の rar.exe を操作できるプログラムは nikpak.exe も操作できます。Total Commander では、Configuration, Packer, Additional packer programs で拡張子 nik を登録し、packer コマンドと unpacker コマンドを nikpak.exe に向けます。無人での展開には -o+ または -y を使用してください。コンソールがない場合、nikpak は上書きするかどうかを尋ねられず、代わりに既存ファイルをスキップするためです。メニュー名は Total Commander のバージョンによって異なります。正確な項目については組み込みヘルプを参照してください。

Windows でスペースを含むフォルダー 末尾がバックスラッシュの引用符付きパス ("C:\My Folder\") は Windows によって誤解析されます (最後の引用符がエスケープと見なされます)。スペースを含む保存先には代わりに -d "C:\My Folder" を使用してください。



3.7 グラフィカルインターフェース

引数なしで (たとえば nikpak.exe のダブルクリックで) 起動した nikpak は、使用方法を表示する代わりに小さなウィンドウを開きます。やることは 1 つ、ドロップされたものを圧縮することです。

  • ファイルまたはフォルダーをドロップ (複数可) するか、円をクリック (または choose files / choose a folder のリンク) してダイアログで選択します。円をクリックすると、リング内に Choose files と Choose a folder の 2 つのボタンが表示されます。それらは最良の圧縮 (-m5) で、ファイル名 (拡張子を除く)、フォルダー名、複数項目の場合はそれらの元のフォルダー名を付けた 1 つのアーカイブに圧縮されます。既存のアーカイブが上書きされることはありません。report.nik は report (2).nik になります。
  • 進行状況 は円形メーター内の大きなパーセント表示で示され、フェーズ (analysing、compressing、finishing)、処理済み量、時間が併記されます。その下の Cancel ボタン (または Esc キー) は長時間の圧縮を直ちに停止し、未完成のアーカイブを削除します。ウィンドウは次の処理のために開いたままです。圧縮中にウィンドウを閉じた場合も同じです。
  • 完了: リングが緑になり、アーカイブ名、元のサイズに対する比率、時間が表示されます。Show in folder は Explorer、Finder、またはファイルマネージャーで開きます。Compress more (または円のクリック) で次を開始します。
  • 保存先: 下部の保存先フォルダーは入力するか Browse で選択できます。次回のために記憶されます (Windows: %APPDATA%\nikpak\settings.txt、macOS: ~/Library/Application Support/nikpak、Linux: ~/.config/nikpak)。初回はデスクトップです。
  • コミュニティ: 右下の 3 つの丸いボタンは nikpak の Telegram、X、Discord ページを開きます (1.5 節)。
  • unNik への切り替え: i ボタンの左にある上向き矢印の丸いボタンは、NikPak を閉じて unNik を起動します (3.9 節)。圧縮後は、このボタンと完了画面の Open in unNik リンクで新しいアーカイブをすぐに開けます。圧縮中はボタンが無効になります。
  • 保存先フォルダーを開く: Save to フィールドと Browse の間にあるフォルダーボタンは、そのフォルダーを Explorer または Finder で開きます。圧縮後は新しいアーカイブを選択した状態で開きます。
  • サウンド: ボタン、リンク、オプションには柔らかいクリック音、各操作 (処理開始、成功、エラー、キャンセル、プログラムの切り替え、ウィンドウ上へのファイルのホバー) には短い音が鳴ります。音声ファイルは使わず、プログラム自身が生成します。タイトルバーのスピーカーボタンでオフ/オンを切り替えられます。既定はオンで、設定は unNik と共有されます。
  • 言語: 左下の、旗と言語自身の名前が付いたボタンは、世界で最も話者数の多い 10 言語 (Ethnologue 2025) のメニューを開きます: English、中文 (標準中国語)、हिन्दी (ヒンディー語)、Español、العربية (アラビア語)、Français、বাংলা (ベンガル語)、Português、Русский (ロシア語)、Bahasa Indonesia。選択すると保存され、その言語で nikpak が再起動します。初回は nikpak は Windows (またはシステム) の言語に従い、なければ English です。コマンドラインは English のままです。
  • 管理者として実行: Windows は、管理者として実行中のプログラムへ Explorer からファイルをドラッグすることを許可しません。nikpak.exe が管理者として (たとえば管理者 PowerShell から) 起動された場合、ドラッグ&ドロップが機能するように、Explorer 経由で通常ユーザーとして一度だけ自身を再起動します。それができない場合は、ウィンドウに通知が表示されます。代わりにボタンでファイルを選択してください。
  • ステータスと About: 左上には EVALUATION COPY · REGISTER (クリックで登録ボックスが開きます) または REGISTERED TO とライセンス保持者が表示されます。右上の最小化と閉じるの隣にある小さな i ボタンは About ボックスを開きます: バージョン、© 2026 Nicolas Choukroun、Nikkoid LLC による配布、ライセンスの状態、Web サイト、ライセンス条件 (LICENSE.txt)。

ウィンドウのサイズは 500 × 560 ポイント (約 9:10) なので、ウィンドウ全体のスクリーンショットはトリミングなしで X (Twitter) の画像投稿に収まります。フレームレスです: 上部をつかんでドラッグします。右上のボタンで About ボックスを開く、最小化、閉じるができます。nikpak.exe を Explorer から起動した場合、Windows が開くコンソールウィンドウは自動的に閉じられます。コマンドプロンプトから起動した場合は、プロンプトはそのまま残されます。グラフィカルディスプレイがない場合 (たとえば SSH 経由)、nikpak は従来どおり使用方法を出力します。インターフェースは egui/eframe を使用し、Inter、Noto Sans SC、Noto Sans Devanagari、Noto Sans Bengali、Noto Sans Arabic 書体のサブセットを内蔵しています (SIL Open Font License、assets/fonts/OFL.txt を参照)。コマンドライン専用の実行ファイルは cargo build --release --no-default-features でビルドされます。

ヒンディー語、ベンガル語、アラビア語 はシェーピングが必要です。文字は形を変えて連結し、母音記号は子音の周囲に移動し、アラビア語は右から左に流れます。egui は 1 文字につき 1 グリフを描画するため、これらの言語は誤って表示されます。そこで nikpak はそのようなテキストを Unicode 双方向アルゴリズム (unicode-bidi) で並べ、rustybuzz (HarfBuzz の Rust ポート) でシェーピングし、ab_glyph でラスタライズして結果を画像として描画します (textshape.rs)。内部のラテン語や数字は Inter フォントのままです。長い翻訳はボタンに収まるよう縮小され、ボックスはテキストに合わせて大きくなります。翻訳 (i18n.rs) は機械支援で作成されました。ネイティブスピーカーによるレビューを歓迎します。

3.9 unNik — 無料のアーカイブブラウザー

unNik (unNik.exe) はパッケージの 2 つ目のプログラムです。.nik アーカイブを開き、内容を表示し、選んだものを展開します。企業を含め誰でも無料で、登録もリマインダーもありません (LICENSE.txt 第 2a 条)。セットアップは nikpak.exe の隣にインストールし、スタートメニューに追加し、.nik ファイルのプログラムとして設定するため、アーカイブをダブルクリックすると unNik で開きます。コマンドプロンプトからは unNik archive.nik でも同じです。

空のウィンドウは NikPak とまったく同じ外観で、リング内に上向きの矢印があります。.nik アーカイブをドロップするか、リングをクリックするか、最近使ったアーカイブの 1 つを選択してください。ウィンドウはブラウザーに拡大します (1120 × 720、端からサイズ変更可能、最大化も可能)。暗号化アーカイブは最初にパスワードを尋ねます。

  • 移動 はフォルダーツリー、パンくず、Back、Forward、Up (Alt+Left、Alt+Right、Backspace)、ダブルクリックで行います。検索 (Ctrl+F) はアーカイブ全体から名前でファイルを検索し、各結果はそのフォルダーを表示します。
  • 選択 はクリック、Ctrl+クリック、Shift+クリック、チェックボックス、Ctrl+A、矢印キーで行います。列タイトルをクリックすると名前、サイズ、種類、日付で並べ替えられます。右クリックで全操作のメニューが開きます。
  • すべて展開、または選択項目の展開 (Ctrl+E): 保存先 (既定ではアーカイブの隣の、アーカイブ名のフォルダー)、フォルダーを保持するかどうか、既存ファイルがある場合の動作 (置き換え、両方保持 (name (1).ext)、スキップ) を選択します。フォルダー内から取り出したファイルは、WinRAR と同様にそのフォルダーのパスなしで作成されます。読み取りは最後に選択したファイルの直後で停止します。
  • 表示 (F3、またはテキストファイルのダブルクリック): 行番号付きのテキスト、ハイライト付き検索、行の折り返し、コピー。バイナリファイルは 16 進表示。最初の 16 MB が表示され、Open in Notepad はファイル全体を開きます。Open はファイルを専用のプログラムで起動します (まず一時フォルダーに展開されます)。
  • 削除 (Del) は確認後にアーカイブからファイルやフォルダーを削除します。アーカイブはソリッドなので、それらを含めずに再書き込みされ、すべて成功した場合にのみ元のファイルを置き換える一時ファイルに書き込まれます。暗号化アーカイブはパスワードを保持し、他のエントリはメディアフィルターまたは Deflate フィルターと -m5 エンジンを保持します。
  • テスト はアーカイブ全体を解凍し、すべてのファイルを検査します。詳細 ペインにはサイズ、日付、フォルダー、CRC32、ファイルの保存方法、属性が表示され、アーカイブ自体についてはサイズ、方式、暗号化が表示されます。ツリー下のサマリーには節約された容量が表示されます。
  • NikPak と同じ 10 言語、言語ボタン、About ボックス (i)、コミュニティボタン。任意の文字体系のファイル名は、フォールバックとしてシステムのフォントで描画されます。
  • NikPak への切り替え: i ボタンの左にある下向き矢印の丸いボタンは、unNik を閉じて NikPak を起動します。両方のプログラムは同じフォルダーにあります。設定ファイルを共有するため、一方で選択した言語が他方でも使われ、既に開いているウィンドウも 2 秒以内に変更に追随します。
  • 保存先フォルダーを開く: 取り出しボタンの左にあるボタンは、最後の展開先フォルダーを Explorer または Finder で開きます (展開前はアーカイブのフォルダー)。unNik は NikPak と同じサウンドを再生し、アーカイブを開く、展開、削除、テストの音があります。スピーカーボタンと NikPak の設定は 1 つを共有します。

3.10 スキン

NikPak と unNik は同じ 55 種類のウィンドウスキンを共有します。Nikkomander の 41 種類 (既定の Nikkoid Blue と Nikkoid Bright から、Dracula、Nord、Solarized、Classic Blue、Matrix、Pizza、Christmas、8-Bit Game まで) に加え、背景をプログラム自身が描画する 14 種類のペイントスキン (Moon、America、Pattaya Neons、Burgers Tokyo、Sushi、Amiga、MSX、Colecovision、ZX Spectrum、Cat Life、Dog Life、Mario Bros、Counter Strike、Chess) があります。

  • スキンボタン (両プログラムのタイトルバーにあるパレット): スキンメニューを開き、各スキンが自身の色で描画されます。スキンにポインターを合わせるとウィンドウ全体でプレビューされ、クリックで確定します。Esc または外側のクリックで元のスキンに戻ります。
  • 太陽 / 月のボタン はその隣にあり、Nikkoid Blue (ダーク) と Nikkoid Bright を 1 クリックで切り替えます。
  • スキンボックスはプログラムの外に置かれます。 ボックスが開いている間、ウィンドウは右側にボックスの幅だけ広がります。プログラムは 500 × 560 のパネルを保ち、ボックスはその横の余分な透明スペースに収まるため、試しているスキンの背後でもインターフェース全体が見えたままです。ボックスはタイトルバーでプログラムの上やウィンドウ内の任意の場所にドラッグでき、Apply Skin と Cancel ボタンがあります。スキンをクリックするとウィンドウ全体で試され、Apply で確定して両プログラム用に保存され、Cancel (または Esc か ×) で元のスキンに戻ります。プログラムをクリックしてもボックスは閉じなくなりました。unNik のウィンドウは広がりません。
  • 選択したスキンは保存され (skin= として設定ファイル内)、共有されます。一方のプログラムで選んだスキンは 2 秒以内に他方でも使われます。
  • 独自のスキン: メニュー下部の「Import a skin…」は Nikkomander の .skin.json ファイル (名前と色のリスト) を読み込み、設定ファイルの隣の skins フォルダーにコピーします。インポートしたスキンのタイル上の × で削除できます。
  • ペイントスキンはインターフェースの背後に退きます。 描画背景は CSS グラデーションではなく src/skin_scenes.rs によって描かれるため、任意のウィンドウサイズに拡大縮小できます。1.6.2 以降、各スキンは src/skin.rs の discreet() パスを通ります。アートは自身の局所平均へ引き寄せられ、軽くぼかされ、スキンの背景色へフェードします。ドロップリングとテキスト列の背後では最も強く、ロゴの上では少し強めに適用されるため、14 種類すべてでタイトル、リング、ステータステキストが鮮明なままです。

3.11 ファイルマネージャーのメニュー

ファイルマネージャーの右クリックメニューに、WinRAR のような「NikPak」サブメニューがセットアップによってインストールされます (Windows: 既定でチェックされるオプション、Linux: nikpak --install-menu、macOS: Finder クイックアクション)。

  • ファイルとフォルダーに対して: Add to archive… (名前とフォルダーを尋ね、NikPak ウィンドウで圧縮します) と Add to archive here (アーカイブは項目の隣に作られ、ウィンドウへのドロップと同じ命名規則になります)。
  • .nik アーカイブに対して: Open with unNik、Extract files…、Extract here、Extract to its own folder。
  • 複数の項目 は 1 つのアーカイブになります。複数のアーカイブを選択した場合は、1 つのウィンドウで順番に展開されます。
  • コマンドは unNik.exe を通じて実行されるため、コンソールウィンドウが一瞬表示されることはありません。ラベルは NikPak の言語に従います。Windows 10 ではサブメニューが直接表示され、Windows 11 では Show more options (Shift+F10) の下に表示されます。Linux では KDE Dolphin のサービスマニュー、Nemo アクション、Nautilus スクリプトが追加され、macOS では Finder クイックアクションが追加されます。
  • メニューが使用する新しいコマンドラインオプション: nikpak --add と --add-here (指定した項目を圧縮)、nikpak --install-menu、--uninstall-menu、--all-users、unNik --extract、--extract-here、--extract-to。Extract here / to its own folder は進行リング付きの unNik の小さなウィンドウ (暗号化アーカイブではパスワードボックス) を表示し、すべて展開すると閉じます。警告とエラーは画面に残ります。
  • 2 つ目のセットアップ unnik--setup.exe は、.nik アーカイブを受け取るだけの人向けに unNik (無料のブラウザー) のみをインストールします。NikPak が既にインストールされている場合はプログラムのみをインストールするため、メニューが二重になることはありません。

3.12 パッケージ: Create Package と Open Package

パッケージ は、アーカイブではなく製品である .nik ファイルです。ファイルとフォルダー、名前、作者、説明、表紙画像、パスワード、エンドユーザーライセンス契約を 1 つのファイルに収め、顧客に渡したり販売したりできます。Nikkosynth のサウンドバンクに対応する NikPak 側の形式で、形は同じですがマジックが異なるため、パッケージが Nikkosynth にインポートされることも、サウンドバンクがパッケージとして開かれることもありません (5.7 節)。

2 つのボックスは NikPak ウィンドウにあり、unNik はそのうち 2 つ目のボックスでパッケージを開きます。

  • Create Package — ウィンドウ上部の、Fast / Medium / Best、§ Legal、▣ Cover と同じ行にあるピル。1 つのボックスがすべてを尋ねます: パッケージ名、作者、説明、パスワード (2 回)、任意の EULA、正方形の表紙画像、保存先フォルダー、梱包するファイル。画像フレームをクリックして表紙を選択し (またはウィンドウに画像をドロップし)、ボックス内でファイルかフォルダーを選択します。ボックスを開いたままウィンドウにドロップしてもよく、画像は表紙に、それ以外はリストに追加されます。
  • 起動間で記憶 — 作者、EULA テキストとそのスイッチ、保存先フォルダーは設定ファイルに保存されるため (package_author、package_eula_on、package_dest、およびその隣の package-eula.txt)、2 つ目のパッケージには名前、ファイル、パスワードだけで済みます。
  • ファイル — 保存先フォルダーの <name>.nik、その名前が使われている場合は <name> (2).nik。パスワードは必須です。ファイル、その名前、サイズはパスワードで暗号化され、Zstandard で圧縮されます。パッケージの書き込みが終わると、ウィンドウは通常どおり緑のリングに前後のサイズを表示します。
  • Open Package — パッケージを NikPak または unNik にドロップするか、ファイルマネージャーから開きます。復号の前に、ボックスが表紙、名前、作者、ファイル数、説明を表示します。次に EULA が表示され、読んで I approve で承認する必要があります。続いてパスワードと保存先フォルダーです。保存先は Create Package と同じ記憶されたフォルダーです。
  • 展開 — すべてのファイルがフォルダーごとに書き出され、CRC32 が検証され、安全でないエントリ名は拒否されます (10.1 節)。処理完了後に保存先を開くことができます。パッケージに EULA が含まれる場合は Terms of use.txt としてフォルダーに書き出されるため、条件はファイルと一緒に移動します。
  • コマンドラインからも同じ — nikpak に渡されたパッケージは拒否されるのではなく、次のように名指しされます: 「This is a NikPak package (500 files, by …), not a NikPak archive. Open it with unNik or NikPak to unpack it.」
  • 混同しないでください — アーカイブ (第 5 章) は汎用のコンテナ、パッケージはライセンス付きの製品、Nikkosynth のサウンドバンクはパッチのバンクです。3 つは最初の 8 バイトで区別されます (5.7 節)。

3.13 分割ボリュームと自己解凍 .exe

1.12 以降、アーカイブは WinRAR ユーザーに馴染みのある方法で、ボリュームのセットまたは 1 つの自己解凍 .exe として配布できます。どちらも配布用 (アーカイブをディスクに入れる、アップロード制限内に収める、何もインストールされていない人の手に渡す) の機能であり、登録版でのみ利用できます。

  • 分割ボリューム。 -v<size> (またはウィンドウの Split ピル) は、アーカイブのバイトストリームを指定サイズのボリュームに分割します — 100 MB、700 MB、1 GB、2 GB、4.7 GB、または入力したメガバイト/ギガバイト数。最初のボリュームは photos.nik、次は photos.n01、photos.n02 … です。展開するには最初のボリュームを展開します。リーダーは photos.n01、photos.n02 … を自動的に追跡します。ちょうどサイズいっぱいになったボリュームには空の後続ボリュームが付き、これによってリーダーは「さらに続く」と「最後」を区別します。
  • 自己解凍。 -sfx は photos.exe を書き出します — アーカイブを追加した unNik と、小さなトレーラーです。実行した人は小さなウィンドウ (名前、サイズ、ボリューム数、展開先フィールド、暗号化時のパスワード、承認する条件、1 つの Extract ボタン) を得て、何もインストールされておらず nikpak も不要な状態で展開できます。-v と -sfx を併用すると photos.exe と photos.n01 … が得られます。
  • 登録版のみ。 分割ボリュームと .exe はアーカイブを配布物にする 2 つの機能であるため、評価版では書き出されません。Split ピルは代わりに登録ボックスを開き、-v / -sfx は何かが書き込まれる前にコマンドラインで拒否されます。
  • アーカイブをドロップして展開。 1.13.1 以降、ウィンドウにドロップされた .nik (または分割セットの任意のボリューム、自己解凍 .exe) は、圧縮する代わりに Extract ボックス (名前、サイズ、ボリューム、パスワード、保存先) を開きます。

4 アーキテクチャ

nikpak は約 9,600 行 (単体テストを含む) の単一の Rust プログラムで、16 個のソースファイルと、非公開のライセンスツール nikpak-keygen から構成されます。中心となる設計原則はストリーミングです。ファイルは 256 KiB 単位で読み込まれ、ライターの連鎖を通され、全体としてメモリに保持されることはありません (唯一の例外は BMP ピクセルデータで、256 MiB に制限されています。またコーデックの 64 KiB 作業バッファーも同様です)。

4.1 アーカイブ作成時のデータフロー

各ステージは、次のステージを包む標準の Write トレイトの実装であるため、同じコードパスが通常のアーカイブ、暗号化アーカイブ、メディア試行に使われます。

4.3 アーカイブ作成の手順

  • 検証 出力先を検証します。既存のアーカイブは -o+ (または対話的な yes) でのみ置き換えられます。それ以外の場合、nikpak は追記がサポートされていないことを説明します。
  • 収集 入力を収集します。ワイルドカードは展開され (PowerShell は行いません)、@listfiles が読み込まれ、除外が適用され、シンボリックリンクと特殊ファイルは警告付きでスキップされ、アーカイブ自体が自分に追加されることはありません。
  • パスワードの解決 暗号化が要求された場合はパスワードを解決し (3.3 節)、Argon2id で鍵を導出します。
  • ヘッダーの書き込み 続いてライターの連鎖を構築します: ファイル、バッファー付きライター、任意のチャンク暗号化器、Zstandard エンコーダー。
  • 各エントリの書き込み。 メディアファイルは検出と試行を経ます (第 7 章)。それ以外は CRC32 を計算しながら 256 KiB 単位でコピーされます。
  • 終端マーカーの書き込み エントリ数を含む終端マーカーを書き込み、Zstandard フレームを終了し、最後の暗号化チャンクを封印してディスクにフラッシュします。
  • 名前の変更 name.nik.tmp を name.nik に変更します。それ以前に何かが失敗した場合、ガードオブジェクトが一時ファイルを削除するため、中途半端に書かれたアーカイブが正常なアーカイブを置き換えることはありません。

4.4 アーカイブ展開の手順

  • ヘッダーの読み取りと検証: マジック、バージョン、フラグ、方式、および暗号化アーカイブの場合は Argon2id パラメーター。これらはメモリを割り当てる前に範囲チェックされます。
  • パスワードの取得 と鍵の導出。最初の認証付きチャンクがパスワードの正否を証明します。
  • エントリストリームの走査。 各エントリ名は、ファイルシステムにアクセスする前にサニタイズされます (10.1 節)。
  • ファイルの書き込み は create_new で行い、タイムスタンプとパーミッションを設定し、再構築されたバイトの CRC32 を検証します。CRC に失敗したファイルは保持されず削除されます。
  • 終端の検証 アーカイブの終端を検証します。終端マーカーの後でストリームが本当に終わっていること、暗号化されている場合は最後の認証付きチャンクが処理されていることを確認します。これにより切り詰めや追記されたデータを検出します。

4.5 メモリとスレッド

Zstandard は圧縮にワーカースレッドを使用します (既定では全コア、-mt<N> で制限)。1.13 以降、最高レベルも並列で動作します: -m5 はバイナリとテキストのエントリを均等なブロック (コアごとに 1 つ、8 MiB 未満にはならない) に分割し、各ブロックを専用スレッドで圧縮します。一方、ファイル単位の処理 (メディア試行、Deflate 再圧縮) はすべてのレベルでワーカースレッドのプール上で実行されます。エンコーダーのメモリは ENCODER_RAM_BUDGET (1.5 GiB) で制限されます。ブロックが多いほど LZMA2/PPMd の辞書は小さくなります。NIKPAK_SEQ=1 で 1 つずつ処理する経路に戻ります。展開、音声コーデック、暗号化は呼び出しスレッドで実行されます。Argon2id は鍵導出に 64 MiB を必要とし、最高レベルでは 128 MiB のマッチウィンドウを使用します。

5 .nik コンテナ形式

.nik ファイルは、小さな固定ヘッダーとそれに続く本体で構成されます。本体は 1 つのソリッドストリームです。すべてのエントリが連結され、まとめて圧縮され、必要に応じて暗号化されます。形式のバージョン 2 はメディアレコードを追加します。バージョン 1 のアーカイブも引き続き読み取れます。

5.3 暗号化本体のフレーミング

暗号化フラグが設定されている場合、zstd の出力は平文 64 KiB のチャンクに分割されます。各チャンクは 32 ビットのビッグエンディアン長に続く暗号文として保存され、Poly1305 タグの分だけ 16 バイト長くなります。チャンクはさらに 1 バイト以上続く場合にのみ封印されるため、最後のチャンクが空になることはなく、最終としてマークできます (8.3 節)。

5.4 なぜソリッドストリームなのか?

すべてのファイルを 1 つのストリームとして圧縮すると、圧縮器はファイル間の繰り返しを見つけられます。これはソースツリーや文書コレクションでは極めて重要です (第 11 章のベンチマークでは、10,949 ファイルで RAR の非ソリッド出力がソリッド出力のほぼ 2 倍の大きさになっています)。代償はシーケンシャルアクセスです。単一ファイルを展開するには、その前にあるものを解凍する必要があります。nikpak はメディアエントリについてはデコードせずにスキップすることで、このコストを軽減します。

5.5 バージョニング

バージョンバイトは、プログラムが理解できる最高バージョンと比較されます。新しいアーカイブでは、誤解を招く破損エラーではなく、Unsupported archive version N; please update nikpak というメッセージが出力されます。不明なフラグ、方式、メディアフィルターも同様に拒否されます。

5.6 マルチエンジン本体 (バージョン 3)

-m5 で作成されたアーカイブは方式 2 を使用します。5.2 で説明した内部レコードストリームは変わりませんが、エントリの間でのみブロックに分割され、各ブロックは独自のエンジンで圧縮されます。解凍されたブロックを連結すると、シングルエンジンアーカイブのレコードストリームとまったく同じになるため、一覧表示、テスト、展開は同じように動作します。

要素レイアウト
bodyblock* に続いて単一の 0 バイト
blockengine:u8 parameters、続いてフレーム [u32 length 1 .. 1 MiB][compressed bytes]、長さ 0 で終了
エンジン 1Zstandard (パラメーターなし)
エンジン 2LZMA2 生ストリーム: 辞書サイズ u32、lc u8、lp u8、pb u8
エンジン 3PPMd バリアント I (PPMd8): 次数 u8、モデルサイズ u32、復元方式 u8 (0 = 再起動)



フレーミングにより、リーダーはデコーダーを信頼せずに各ブロックの終端を見つけられ、すべてのパラメーターはメモリを割り当てる前に範囲チェックされます (LZMA2 辞書は最大 1.5 GiB、PPMd モデルは最大 1 GiB、次数は 2〜16)。暗号化されている場合、本体は他のアーカイブと同じ認証付きチャンクで保護されます (第 8 章)。

5.7 パッケージコンテナ (NIKPACK2)

アーカイブ (本章) と Nikkosynth サウンドバンクのほかに、.nik は NikPak パッケージ (3.12 節) である場合があります。3 つは拡張子を共有するため、すべてのプログラムは最初の 8 バイトでファイルを識別します:

パッケージとサウンドバンクは同じ方法で構築されます (平文の JSON ヘッダー 1 行と、その後に封印された本体 1 つ)。しかしマジックが異なるため、2 つの製品は区別されます。

ヘッダーは 1 行の JSON で、意図的にパスワードなしで読めるようになっています。Open Package ボックスがパスワードを求める前に表示する内容です。format (「nikpak-package」)、version (1)、name、author、description、eula、cover (1024 × 1024 の JPEG または PNG の base64) と coverType、count、encrypted、暗号化されている場合は 16 バイトの salt と nonce (16 進) を含みます。ファイルに関する情報は含まれません。ファイル名と内容は本体内にあります。ヘッダーはタグの対象の一部であるため、EULA が編集または削除されたパッケージは開けなくなります。

本体は 5.2 節のレコードストリームです。同じレコード 1 FILE、2 DIR、0 END で、64 ビットのサイズ、mtime、mode、ファイルごとの CRC32 を持ち、1 つの Zstandard ストリーム (レベル 19) として圧縮されます。パッケージには MEDIA レコードも Deflate 再圧縮もありません。ファイルはそのまま保存され、ストリーム全体が一度に圧縮されるため、両方の製品が実装できるほど形式が小さく保たれます。

  • 鍵 — salt ‖ password に対して SHA-256 を 600 000 回反復し、32 バイトの暗号化鍵と 32 バイトの検証鍵に分割します。推測 1 回に 0.5 秒かかり、これが盗まれたパッケージへの攻撃を高コストにします。
  • 本体 — キーストリーム SHA-256(encryption key ‖ nonce ‖ counter) との XOR を 32 バイトずつ行います。
  • タグ — ヘッダー行と暗号文に対する HMAC-SHA-256 で、末尾 32 バイト。定数時間で比較されます。誤ったパスワードと破損ファイルは同じように失敗するため、両者を区別できません。
  • なぜ Argon2id と XChaCha20-Poly1305 ではないのか — パッケージは共有形式だからです。Nikkosynth のバンクも同じ構造を使っており、両方の製品が標準ライブラリのコード数十行で実装できる必要があります。これは封印されたコンテナ (書き手は 1 人、読み手は 1 人、攻撃者が選んだメッセージはなく、パスワードが移動することもない) であり、そうあるべきなのです。

制限: 説明 4 KB、EULA 64 KB、作者 256 バイト、パッケージ名 256 バイト、表紙 4 MB、エントリ名 4096 バイト、展開後の本体 512 MB (付録 A)。

5.8 分割ボリュームと SFX トレーラー

分割セットは 2 つ目の形式ではありません。ボリュームは、アーカイブ自身のバイトストリームをサイズ境界で切ったものです。形式の中で分割を認識するのは 1 つのヘッダーフラグだけです。最初のボリュームがアーカイブそのもの (ヘッダーにボリュームサイズを持つ完全な .nik) で、残りは純粋な継続です。

ヘッダー。 フラグビット 3 (FLAG_SPLIT) と、表紙の後の 64 ビットのボリュームサイズ。アーカイブが暗号化されている場合、ボリュームサイズは AAD の一部であり、ボリュームが失われたときに「切り詰められたアーカイブ」ではなく「アーカイブは photos.n01 に続いていますが、それが見つかりません」とリーダーが言えるようにするものです。古いリーダーはアーカイブを拒否しますが、これは正しい動作です。サイズがないと、セットは破損ファイルのように見えるためです。

Chain リーダー。 split::Chain は、最初のボリュームの先頭 (.exe 内の場合はそのオフセット) から開始し、ボリュームの終端に達すると次のボリューム (photos.n01、photos.n02、…、続いて .100 …) を開いて続行する Read です。プログラム内のすべての読み取り経路がこれを通るため、一覧表示、表示、展開、右クリックメニューはすべてセットの全ボリュームを読み取ります。

Out ライター。 split::Out は -v と -sfx の背後にあるライターです。….tmp ファイルに書き込み、finish() で名前を変更するため、失敗した実行が中途半端なボリュームを残すことはありません。1 つのファイル、ボリュームのセット、または .exe を書き出します。

自己解凍。 .exe は unNik.exe のバイト列にアーカイブのバイト列と 40 バイトのトレーラー (マジック NIKPAKSFX、アーカイブのオフセットと長さ、全体サイズ、CRC32) を続けたものです。unNik は起動時に自身の実行ファイル内でこのトレーラーを探し、見つかった場合はドロップウィンドウの代わりに小さなボックスを表示します。.exe は約 8 MB にアーカイブのサイズを加えたものです。

6 圧縮エンジン

6.1 なぜ Zstandard なのか

Zstandard は LZ77 マッチングと、ハフマン符号化と有限状態エントロピー (FSE) からなるエントロピー段階を組み合わせています。ZIP の Deflate アルゴリズムと比較して、はるかに大きなウィンドウでマッチを見つけ、リテラルとマッチ長をより厳密なエントロピー符号でモデル化し、毎秒ギガバイト級の速度でデコードします。また、オープンで広く監査された形式であるため、nikpak のデータを独立したツールで復元できます。

6.2 レベルの対応

nikpak は RAR 形式のレベル (-m0 .. -m5) と zip 形式のレベル (-0 .. -9) の両方を受け付け、Zstandard のレベルに対応付けます:

オプションZstandard レベル特性
-m0なし (保存)圧縮なし、メディアフィルターなし
-m11最速
-m23高速。1 コアで 197 MB を約 0.9 秒 (1.2.0 までの既定)
-m39良好なバランス
-m415高。128 MiB ウィンドウと長距離マッチング。Deflate 再圧縮 (7.9)
-m5 (default)LZMA2 / PPMd最大。1.2.1 以降の既定で、マルチエンジン本体 (6.7) と Deflate 再圧縮



zip 形式のレベルは次のように対応します: -0 は保存、-1 から -6 は Zstandard の 1 から 6、-7 は 9、-8 は 12、-9 は -m5 と同じです。

6.3 大きなウィンドウと長距離マッチング

Zstandard レベル 15 以上では、nikpak は 2^27 バイト (128 MiB) のマッチウィンドウと長距離マッチングを有効にします。ソースツリー、文書セット、バックアップには、ストリーム内で遠く離れた多数の類似ファイルが含まれます。通常の 8 MiB ウィンドウではそれらをまたいで見ることはできません。197 MB のテストセットでは、これにより -m5 の出力が 26.3 MB から 24.4 MB に、-m4 が 29.5 MB から 26.8 MB に減少し、-m4 では速度の低下はなく、-m5 ではわずかでした。2^27 のウィンドウは Zstandard の既定のデコーダー制限内であるため、標準のデコーダーならどれでもデータを読み取れます。

6.4 マルチスレッド

エンコーダーは入力をジョブに分割し、ワーカースレッド (既定では全コア) で実行します。そのため圧縮速度はコア数に応じて向上し、形式は単一のストリームのままです。1.13 以降、-m5 はさらにアーカイブをコアごとに 1 ブロックへ分割し、ブロックを並列に圧縮します (4.5 節)。ファイル単位のパイプラインはすべてのレベルで動作します。本書のすべての数値は1 つのコアで測定されたものです。一般的なマルチコアマシンでは、nikpak はここに示したよりかなり高速です。

6.5 ストリーム内の完全性

Zstandard フレームは独自のコンテンツチェックサムを持ち、nikpak はファイルごとの CRC32 と、エントリ数を含む終端マーカーを追加します。そのため、破損した平文アーカイブは 3 つのレベルで検出されます: フレームのチェックサム、ファイルごとの CRC、終端マーカーです。

6.6 保存モード

-m0 はエントリを非圧縮で書き込みます。既に圧縮されたデータに有用であり、意図的にメディアフィルターをバイパスする唯一のモードでもあります。保存 を求めたユーザーはデータが変換されることを期待していないためです。

6.7 最高レベル: LZMA2 と PPMd

Zstandard は速度のための正しいエンジンですが、最強の設定でもソースコードや文書では LZMA2 に数パーセント劣り、散文では PPMd に大きく劣ります。そのためバージョン 1.2 以降、-m5 はブロックからアーカイブを構築します (形式は 5.6):

  • バイナリブロック。 フォルダー、バイナリファイル、メディアエントリ、Deflate 再圧縮されたエントリは LZMA2 で圧縮されます: プリセット 9、ナイス長 273、マッチファインダー深度 32、データに合わせた辞書サイズ (1〜128 MiB)。
  • テキストブロック。 最初の 64 KiB に 0 バイトがなく、制御文字がほとんどないファイル (ソースコード、テキスト、CSV、HTML、XML など) は 2 つ目のブロックに送られます。これらのファイルの連続する 1 MiB の 4 つの範囲が、PPMd バリアント I (次数 8、192 MiB モデル) とテキスト向けに調整した LZMA2 (lc 4、pb 0) で試行圧縮され、小さい方の結果が採用されます。散文は PPMd に有利で、類似ファイルの多い大規模なソースツリーは LZMA2 に有利です。ファイル間の長い繰り返しをコピーできるためです。
  • 順序。 各ブロック内では、7-Zip と同様にファイルが拡張子、次にファイル名で並べられ、同一または類似のファイルが隣り合うようにされます。連続した試行サンプルと合わせて、これにより一般データセットが 7.5 % 小さくなりました。

「極端」な LZMA2 設定は測定のうえ却下されました。表計算の XML では最大 10 倍遅く、しかも小さくならなかったからです。1.13 以降、-m5 アーカイブのブロックはコアごとに 1 つ、並列に圧縮されます。-mt<N> はブロック数を設定します (最高の圧縮率には 2、速度には 8)。

7 メディアインテリジェンス

汎用の圧縮器はバイトを見るだけです。WAV ファイルが、次のサンプルが前のサンプルから予測できる波形であることや、写真の隣接ピクセルがほぼ等しいことを知りません。nikpak のメディア層がその知識を提供します。そのようなファイルを認識し、冗長性をあらわにする可逆変換を適用し、圧縮器 (または専用コーデック) がそれを活用できるようにします。nikpak が RAR に対して最も優位に立つのはこの部分です。

7.1 内容による検出

検出は 8 KiB 以上の各ファイルの先頭バイトを調べ、拡張子は決して信頼しません。そのため .dat に名前を変えた WAV も見つかり、.wav という名前のテキストファイルは見つかりません。

7.2 試行: ファイルごとに最良のフィルターを選ぶ

すべてのファイルに最適な単一の変換はありません。予測符号化は録音音楽で勝ち、バイトプレーン分離は 8 ビット・コンパンディング由来の音声 (約 1,000 個の異なる 16 ビット値しか現れない) で勝ち、通常の圧縮は無音や非常に反復的なトラッカーサンプルで勝ちます。そのため nikpak は推測せずに測定します。

  • サンプルを取ります。サンプル領域が 3 MiB 以下なら全体、それ以上なら音声の 5 %、45 %、85 % の位置の 768 KiB の 3 つのウィンドウ。画像の場合は先頭の行から約 4 MiB まで。
  • サンプルを通常の Zstandard レベル 3 (ベースライン) と、該当するすべてのフィルターで圧縮します: 16/24/32 ビット音声には NAC、Shuffle、Shuffle+Delta、8 ビット音声には NAC と Shuffle+Delta、画像には MED。
  • 推定値が最小のフィルターを採用しますが、ベースラインを少なくとも 2 % 上回る場合に限ります。そうでなければファイルは通常の圧縮で保存されます。
  • 勝った方法でファイルを書き込みます。これはすべてファイルごとに行われるため、1 つのアーカイブに、異なる方法で符号化された WAV と通常のファイルが同居できます。

nikpak mt は同じ測定をファイル全体に対して実行し、表を出力します。第 11 章のベンチマークはこうして調べられました。オプションでは、-mc- はフィルターを無効にし、-mc+ は試行なしで既定のフィルターを強制します。

可逆で、検証され、回避可能 すべてのフィルターは正確に可逆です。各エントリとともに保存される CRC32 は元のバイトに対して計算され、展開時にチェックされます。NAC エンコーダーは書き込み中に各ブロックを検証し (7.4 節)、-mc- はレイヤー全体をオフにします。



7.3 NAC 音声コーデック

NAC (nikpak audio codec) は、整数 PCM 向けのブロックベースの可逆コーデックです。FLAC と同じ系統で、線形予測と Rice 符号化を行います。このアーカイブ用に設計された独自のビットストリームを持ち、WAV、AIFF、MOD ファイルのサンプルデータに使用されます。

ブロックとステレオのデコリレーション

音声は 4096 サンプルフレームのブロックに分割され、それぞれ独立して符号化されます。これによりコーデックは堅牢になり (エラーが広がらない)、エンコーダーは変化する素材に適応できます。ステレオの場合、エンコーダーはブロックごとに 4 つの表現から 1 つを選びます:

モード符号化するチャンネル再構築
0Left, Right直接
1Left, SideR = L - S
2Side, RightL = R + S
3Mid, Sidesum = (M << 1) | (S & 1)、L = (sum + S) >> 1、R = (sum - S) >> 1



ここで Side = L - R、Mid = (L + R) >> 1 です。サイドチャンネルは通常のチャンネルより 1 ビット多く必要で、bits + 1 で符号化されます。モードの選択は低コストで、エンコーダーは L、R、M、S の 2 次固定予測残差の絶対値を合計し、合計が最小のペアを選びます。チャンネル相関の強い録音では、Mid/Side により通常数パーセント節約できます。

無駄なビット。 ブロック内のすべてのサンプルの下位ビットが常に 0 の場合 (16 ビットコンテナに格納された 8 ビット録音、または量子化された信号)、それらは除去され、その数が 5 ビットで保存されます。

固定予測器

order 0: e[i] = x[i]
order 1: e[i] = x[i] - x[i-1]
order 2: e[i] = x[i] - 2*x[i-1] + x[i-2]
order 3: e[i] = x[i] - 3*x[i-1] + 3*x[i-2] - x[i-3]
order 4: e[i] = x[i] - 4*x[i-1] + 6*x[i-2] - 4*x[i-3] + x[i-4]



ブロックの最初の order 個のサンプルは、ウォームアップ値としてそのまま保存されます。

線形予測符号化 (LPC)

倍音や和声のある音楽では、ブロックに適合させた係数を持つ予測器の方が固定多項式よりはるかに優れています。エンコーダーは次のように係数を計算します:

  • ブロックに Tukey 窓 (最初と最後の 4 分の 1 をテーパー) を適用し、端が統計を歪めないようにします。
  • 窓かけされた信号の自己相関 r[0..32] を計算します。
  • Levinson-Durbin 再帰 を実行します。これにより 1 回のパスで 1〜32 次すべての最適な係数セットが得られます: k = (r[i] - sum a[j] r[i-j]) / err、a[i] = k、a[j] = a[j] - k a[i-j]、err = err (1 - k^2)。
  • 実数の係数を 12、14、15 ビットの精度 (サンプル幅による) で整数に量子化し、最大の係数がちょうど収まるように 2 のべき乗のスケール (shift、0〜20) を選びます。丸めには誤差フィードバックを使うため、量子化誤差が係数間で蓄積しません。
  • いくつかの次数 (セットは下記のエフォートレベルによる) を評価し、それぞれの残差を計算し、係数の送信コストも含めて推定合計サイズが最小のものを採用します。

予測器自体は純粋な整数演算で、デコーダーが実行するのはこれです:

pred[i] = (q[0]*x[i-1] + q[1]*x[i-2] + ... + q[n-1]*x[i-n]) >> shift
e[i] = x[i] - pred[i] (n = order; the sum uses 64 bits)



浮動小数点は、どの整数係数を送るかを決めるためにエンコーダーだけが使用します。デコーダーは浮動小数点に触れないため、デコードはあらゆるプロセッサとコンパイラでビット単位で正確です。

残差符号化

予測誤差はジグザグ変換 (u = (e << 1) XOR (e >> 63) で、小さな正負の値が小さな数になる) で符号なし数に変換され、分割 Rice 符号で符号化されます。ブロックの残差は 2^p 個のパーティション (p は 0〜8、エンコーダーが選択) に分割され、各パーティションに独自の Rice パラメーター k (5 ビット) が与えられます。値は u >> k を単進 (その数の 0 と 1 つの 1) で書き、続いて下位 k ビットを書きます。パーティションの最良の k はその値の合計から導出されるため、各候補予測器のコストは符号化せずに実行中の合計から安価に見積もれます。

アーカイブのレベル (-m オプション) は、ブロックごとに試す LPC 次数の数を決めます。次数が多いほど結果はわずかに小さくなり、エンコーダーは遅くなりますが、デコーダーの速度は同じです。

7.4 自己検証

アーカイブの書き込みはエンコーダーのバグを検出できる唯一の機会であるため、NAC エンコーダーは自分自身を信頼しません。各ブロックを符号化した後、そのブロックを再度デコードし、元のサンプルと比較します。相違があれば、ブロックを verbatim (失敗し得ない) として再符号化して再度チェックします。それすら失敗すれば、アーカイブ処理は明示的なエラーと -mc- の使用提案とともに停止します。フォールバック経路は単体テストで実行され、ビット深度とチャンネル数のすべての組み合わせで verbatim 符号化を強制します。この仕組みにより、起こり得る無言のデータ損失バグが、検出・回復可能な状態に変わります。

さらに、デコーダーはファジングされます。単体テストでは、ランダムなバイトのブロックやビットを反転したブロックが数千個与えられ、パニックや不合理な量のメモリ割り当てなしにエラーを返さなければなりません。開発中、これにより実際のバグが 1 つ見つかりました (32 ビット素材では Rice パラメーター探索が空になり、数ギガバイトのコードを生成するパラメーターにフォールバックする可能性がありました)。修正済みで、テストでカバーされています。

7.5 Shuffle と Shuffle+Delta

予測に反応しない音声もあります。ベンチマークで使用したギャラリーの WAV ファイルは 16 ビットですが、コンパンディングされた 8 ビット音源から作られたため、異なるサンプル値は約 1,000 個しかありません。予測器ではそれを活用できず、FLAC は元の 84 % に圧縮しますが、通常の Zstandard では 63 % 必要です。役立つのは、圧縮器が均質なデータを見るようにバイトを並べ替えることです:

  • Shuffle はサンプルのバイトをプレーンに分離します。チャンネル 0 のすべての最下位バイト、次にチャンネル 0 のすべての最上位バイト、次にチャンネル 1、という順で、32768 フレームのブロック単位で行います。上位バイトプレーンは滑らかで、下位バイトプレーンは非常に限られたアルファベットを持ち、Zstandard のエントロピー符号化器はインターリーブされた混合よりもそれぞれをはるかによくモデル化します。
  • Shuffle+Delta はまず各サンプルを同じチャンネルの前のサンプルとの差分に置き換え (サンプル幅を法とし、ブロックをまたいで状態を引き継ぐため正確に可逆)、次にシャッフルします。これは信号が滑らかでも NAC が勝つほど予測可能でない場合に役立ちます。

35 個のギャラリーファイルでは、ファイルごとに最良のフィルター (試行で選択) を使ったアーカイブは、-m2 で元のサイズの 51 %、-m5 で 47 % となり、通常の Zstandard の 63 % を上回ります。

7.6 ProTracker MOD ファイル

MOD モジュールは 1084 バイトのヘッダー (タイトル、31 個のサンプル記述子、128 エントリのパターンオーダーテーブル、オフセット 1080 の 4 バイトシグネチャ)、続いてパターンデータ、続いてすべての楽器の生の 8 ビット符号付きサンプルで構成されます。nikpak はサンプルの開始位置と長さを計算します:

patterns = max(order table) + 1
sample_start = 1084 + patterns * 256 * channels (4 ch: 1024 B per pattern)
sample_bytes = sum of (length in words * 2) over the 31 descriptors,
clamped to the end of the file



ヘッダーとパターンはそのまま保存され (圧縮器はその反復的な音符イベントをうまく扱います)、サンプル領域は試行のために単一のモノラル、符号付き、8 ビットストリームとして扱われます。ファイルごとに NAC、Shuffle+Delta、または通常の圧縮が勝ちます。サンプリングされた楽器は主に NAC に有利で、一部のモジュール (非常に短い、または非常に反復的なサンプルを持つものなど) では通常の圧縮が勝ちます。切り詰められたモジュールは、実際に存在するデータに領域をクランプして処理されます。

7.7 BMP 画像

非圧縮の BMP は、4 バイトの倍数にパディングされたピクセル行を保存します。フィルターは 4 つのステップで動作します:

  • 分離 ピクセル領域をチャンネルごとに 1 つのプレーン (B、G、R、32 ビットの場合は A) に分割し、行ごとのパディングバイトは別に記憶します。
  • 色のデコリレーション。 青と赤のプレーンから緑のプレーンを減算します (法 256)。写真では 3 つのチャンネルが強く相関しているため、差分は小さくなります。
  • 各ピクセルの予測 を、LOCO-I 画像符号化器で使われている MED (median edge detector) 予測器で隣接ピクセルから行います。左を a、上を b、左上を c とすると、予測は c >= max(a,b) なら min(a,b)、c <= min(a,b) なら max(a,b)、それ以外は a + b - c です。予測誤差がピクセルを置き換えます (法 256)。エッジでは予測器はエッジに沿い、滑らかなグラデーションではグラデーションを外挿します。
  • 連結 残差プレーンとパディングバイトを連結し、Zstandard に圧縮させます。滑らかな領域はゼロに近いバイトの連続になります。

デコーダーはステップを正確に逆順に実行します。8 ビット BMP は色のステップを省略し、そのパレットに対して予測が役立つかどうかは試行が判断します。パレットインデックスの予測はグレースケールや滑らかに並んだパレットでのみ意味があるためです。256 MiB を超える BMP ファイルは、メモリ使用量を制限するためにフィルターされません。

7.8 なぜこれが RAR を上回るのか

RAR は汎用のマッチングとハフマンのエンジンに少数のバイトフィルターを加えてメディアを圧縮します。nikpak は代わりに、音声にはブロックごとのステレオデコリレーションと適応 Rice 符号化を備えた真の予測コーデックを、画像には色デコリレーションを備えた適切な 2 次元予測器を与え、ファイルごとに測定で選択します。その結果はベンチマークに表れています。あらゆる種類の音声で 12〜15 % 小さく、トラッカーミュージックで 13 %、写真で 39 % 小さく、ステレオトラックの NAC の結果は専用の FLAC エンコーダーと 0.2 % 以内です。

7.9 Office 文書、PDF、gzip: Deflate 再圧縮

現代の Office ファイルは XML の ZIP アーカイブ (docx、xlsx、pptx、odt、ods) であり、PDF ファイルはページを Deflate (FlateDecode) ストリームに保存します。したがって内容は既に圧縮されており、どのアーカイバも大きくは縮められません。1.1 のベンチマークでは、6.6 MB の .xlsx ファイルは 7-Zip でも 5.6 MB にしかなりませんでした。nikpak 1.2 はその障害を取り除きます。

  • 内容による検出。 ファイル先頭の ZIP ローカルヘッダー (PK\x03\x04)、%PDF-、または gzip ヘッダー。拡張子は決して使用しません。
  • デコード。 すべての Deflate ストリーム (方式 8 の ZIP エントリ、zlib ヘッダーを持つ PDF ストリーム、すべての gzip メンバー) が見つけられ、preflate (Microsoft の preflate-rs) で解析されます。preflate は平文データと、元のエンコーダーがどのように選択したかを正確に記述する小さな修正レコードを返します。どのエンコーダーであっても同様です。
  • 保存。 ファイルは生セグメントと (平文、修正) ペアの連続として保存されます。次に平文の XML またはページ記述がソリッドストリームに入り、LZMA2 が Deflate 時のサイズのほんの一部に圧縮します。
  • 検証。 結果を使用する前に、nikpak はすべての Deflate ストリームを再構築し、ファイル全体の長さと CRC32 を元のものと比較します。何かが異なる場合、または preflate が不正なファイルで失敗したりパニックしたりした場合、ファイルは単に通常どおり保存されます。
  • 展開。 Deflate ストリームはビット単位で再作成されるため、展開された .docx や .pdf はバイト単位で同一であり、CRC32 はすべてのエントリと同様にチェックされます。

11.7 節の Office セットでは、これが nikpak を他のどのアーカイバよりも小さくする理由です。6.6 MB の .xlsx ファイルには、デコードすると 71 MB の XML が含まれており、その XML は Deflate よりもはるかによく圧縮されます。代償は時間です。preflate は 1 秒あたり約 15 MB の平文データを解析します。そのため再圧縮は -m4 と -m5 でのみ使用され、そこでは効果を発揮します (測定: -m3 では 6 倍の時間で 0.5 % の改善)。制限: ファイルは最大 512 MiB、ストリームあたり平文データ最大 512 MiB、修正最大 64 MiB。-mc- でオフにできます。

8 暗号化

nikpak の暗号化は、標準的で十分に研究された構成要素 (Argon2id と XChaCha20-Poly1305 の RustCrypto 実装) のみから構築されています。このプロジェクトのために新しいプリミティブを発明したものはなく、作業はそれらを正しく組み合わせることです。

8.1 脅威モデル

設計は、アーカイブファイルを入手し、自由に調査・改変でき、オフラインで無制限にパスワードを推測できる攻撃者を想定しています。nikpak が保証を目指すのは次のとおりです:

  • 機密性: ファイルの内容と、それに関するすべて (名前、サイズ、タイムスタンプ、パーミッション、ファイル数) の機密性。
  • 完全性と真正性: データ、ヘッダー、データの順序、長さのいずれに対する変更であっても、誤ったデータが受け入れられる前に検出されます。
  • 推測耐性: すべてのパスワード推測が実用的な範囲で可能な限り高コストになります。

アーカイブの存在やおおよそのサイズを隠すものではなく、アーカイブを作成・開くマシン上のマルウェアや、弱いパスワードから保護することもできません。

8.2 パスワードから鍵へ: Argon2id

パスワードは良い鍵ではありません。短く、予測可能で、人間が入力するものです。それを Argon2id で 256 ビットの鍵に変換します。Argon2id は Password Hashing Competition の勝者であり、RFC 9106 で標準化されたアルゴリズムです。Argon2id は意図的にメモリハードです。1 つの鍵の計算には大きなメモリブロックが必要で、それが埋められ、その後データ依存のパターンで繰り返し読み出されます。nikpak は RFC の低メモリプロファイルを使用します:

パラメーター値意味

パス数3メモリは 3 回処理される
レーン数41 回の導出内での並列度
ソルト16 バイトのランダム値アーカイブごとに新規。同じパスワードでも異なる鍵になり、事前計算テーブルは役に立たない

メモリハード性が、Argon2id を古い PBKDF2 (RAR5 や ZIP の AES モードで使用) と分かつものです。PBKDF2 はほとんどメモリを必要としないため、グラフィックスカードや専用チップで膨大な数の推測を並列に試せます。Argon2id では、攻撃者のハードウェアは並列推測 1 回につき 64 MiB を供給しなければならず、その優位性のほとんどが失われます。正規のユーザーのコストは 1 秒の何分の 1 かで、アーカイブごとに 1 回だけ支払います。

パラメーターはヘッダーに保存されるため、将来のバージョンで古いアーカイブを壊さずに引き上げられます。読み取り時にはまず範囲チェックが行われ (メモリはレーン数 × 8 で最大 1 GiB、パス数 1〜64、レーン数 1〜64)、悪意のあるアーカイブがパスワードをチェックする前に nikpak に不合理な量のメモリを割り当てさせることはできません。

8.3 STREAM 構築法における XChaCha20-Poly1305

本体データは XChaCha20-Poly1305 で保護されます。これは関連データ付き認証暗号 (AEAD) です。ChaCha20 は 256 ビット鍵のストリーム暗号を提供し、X バリアントは nonce を 192 ビットに拡張し (繰り返すことなくランダムに選べるほど大きい)、Poly1305 は封印された各メッセージに 128 ビットの認証タグを追加します。ChaCha20 は特別な命令なしであらゆる CPU で高速であり、テーブルベースの AES と違ってキャッシュタイミングリークが本質的にありません。

アーカイブは 1 つのメッセージよりはるかに大きいため、nikpak は STREAM 構築法 (現代のファイル暗号化ツールが使うものと同じ) を使用します。データは 64 KiB のチャンクに分割され、チャンク番号 i は次の nonce で封印されます

nonce (24 bytes) = random prefix (19 bytes)
| chunk counter (4 bytes, big endian)
| last-chunk flag (1 byte)



これにより一度に 3 つの保証が得られます。各チャンクは一意の nonce を持ち、これはストリーム暗号に不可欠です。カウンターが nonce の一部であるため、チャンクの並べ替えや複製は認証に失敗します。最後のチャンクは異なるフラグを持つため、アーカイブを切り詰めると、たとえチャンク境界で正確に切っても、認証に失敗します。新しい最後のチャンクは非最終として封印されているからです。19 バイトのプレフィックスはアーカイブごとにランダムです。

さらに、完全なアーカイブヘッダー (バージョン、フラグ、方式、Argon2id パラメーター、ソルト、nonce プレフィックス) が各チャンクに関連データとして渡されます。認証されますが暗号化はされず、そのどのビットを反転してもすべてのチャンクが失敗します。これにより、保存されたパラメーターを弱めようとするダウングレード攻撃も阻止されます。

8.5 パスワードの扱い

  • 最小長。 アーカイブ作成時は 8 文字。短いパスワードは説明付きで拒否されます。
  • 確認。 対話プロンプトは 2 回尋ね、入力文字をエコーせず、不一致を拒否します。
  • 生成。 パスワードがない場合、nikpak は紛らわしい文字 (0/O、1/l/I) を除いた 56 記号のアルファベットから 24 文字を、オペレーティングシステムの暗号論的に安全な乱数生成器に対する棄却サンプリングで選びます。どの記号も他より出現しやすくならないようにするためです。これは 24 x log2(56)、約 139 ビット のエントロピーで、明確に印を付けたボックスに一度だけ表示されます。
  • メモリの衛生。 導出された鍵とパスワード文字列は、不要になったときにメモリから消去されます (zeroize クレート)。
  • 経路。 コマンドライン (-p)、環境変数 NIKPAK_PASSWORD、対話プロンプト、またはターミナルがない場合は標準入力。コマンドライン形式は便利ですがプロセス一覧に見えるため、他の形式の方が望ましいです。

8.6 攻撃テスト

暗号化アーカイブに対する以下の操作は、完成したプログラムに対して実施されました。すべて、誤ったデータが受け入れられる前に検出されました:

256 ビットの対称鍵は、NIST の耐量子標準化における最高セキュリティカテゴリー (カテゴリー 5) の基準です。NIST が標準化した公開鍵アルゴリズムは、256 ビット AES 鍵の全数探索の難しさにどれだけ近いかで評価されます。言い換えれば、nikpak のデータ暗号化は既に、耐量子標準が目指す強度に達しています。

9.3 パスワードはどうなのか?

暗号の鍵空間は 256 ビットですが、鍵はパスワードから導出されるため、実際の強度はパスワードのエントロピーと 256 ビットの小さい方です。量子攻撃者に対しては、パスワードのエントロピーは攻撃者にとって最良の場合でも半減します:

9.4 「今収穫し、後で復号する」

よく引用される量子の脅威は、攻撃者が今日暗号化されたデータを記録し、量子コンピューターが存在するようになったときに復号するというものです。TLS 接続やメール暗号化のように RSA や楕円曲線で鍵を交換するシステムでは、これは現実的です。nikpak アーカイブには鍵交換がありません。鍵はユーザーの頭かパスワードマネージャーから決して出ない秘密から導かれます。保存されたコピーは、その秘密を推測することによってのみ後で開けられ、量子コンピューターがそれを根本的に容易にすることはありません。

9.5 正直な限界と今後の道

  • 「耐量子」とは、これらのプリミティブに対して汎用探索を上回る既知の量子アルゴリズムが存在しないという意味です。証明ではありません。ChaCha20 と Argon2 の解読研究は続いており、形式はバージョン管理されているため、パラメーターやアルゴリズムを変更できます。
  • 公開鍵による共有 (受信者の鍵にアーカイブを暗号化する) が将来追加される場合は、X25519 と ML-KEM を組み合わせたハイブリッド方式を使用し、どちらか一方が安全であれば全体が安全になるようにします。
  • 耐量子性は実装エラーから保護するものではありません。8.6 節と第 10 章を参照してください。

10 堅牢化と堅牢性

アーカイバは見知らぬ人が書いたファイルを読み、ユーザーのディスクにファイルを書き込むため、典型的な攻撃対象になります。nikpak はすべてのアーカイブを信頼できない入力として扱います。

10.1 安全な展開

  • パストラバーサル (「zip slip」)。 すべてのエントリ名が正規化されます。バックスラッシュはスラッシュになり、空の構成要素と . の構成要素は削除され、.. の構成要素があるとエントリは警告付きでスキップされます。絶対名はルートを失うため、/etc/passwd は保存先フォルダーの内側に展開されます。
  • Windows の名前。 Windows で実行する場合、< > : " | ? * や制御文字を含む構成要素、スペースやドットで終わる構成要素、予約デバイス名 (CON、PRN、AUX、NUL、COM1-9、LPT1-9) と等しい構成要素は拒否されます。
  • シンボリックリンク。 書き込みの前に、保存先より下の対象パスの既存のすべての構成要素がチェックされ、リンクが辿られることはありません。既存ファイルはまず削除され、新しいファイルは create_new で作成されます。これは既存パスを開くことを拒否するため、リンクを使って書き込みをリダイレクトすることはできません。
  • 特権ビット。 Setuid、setgid、スティッキービットは決して復元されません。パーミッションは通常の rwx ビットにマスクされます。
  • 失敗したファイル。 CRC32 が一致しないファイルは削除され、残されることはありません。

../../evil.txt、/tmp/evil.txt、..\..\evil.txt、ok/../../evil.txt を含む手作りアーカイブがテストで展開されました。保存先の外に出たものはなく、安全でないエントリは報告されてスキップされ、保存先に仕込まれたシンボリックリンクは拒否されました。

10.2 境界付きデコーダー

  • Argon2id パラメーターは、割り当ての前に範囲チェックされます (8.2 節)。
  • 暗号化チャンクの長さは 16 バイトから 64 KiB + 16 の間でなければならず、名前は最大 4096 バイト、音声ブロックは妥当な長さを宣言しなければならず、BMP 領域は 256 MiB に制限され、単進 Rice 符号には上限があります。
  • 音声およびメディアのデコーダーは単体テストで数千のランダム入力とビット反転入力を受け、エラーを返さなければならず、決してパニックやアボートを起こしてはなりません。
  • nikpak 自身のコードには unsafe ブロックがなく、Rust の境界チェックにより、C ではメモリ破壊バグになるようなロジックエラーもクリーンな失敗に変わります。

nikpak はアーカイブの展開比率を制限しないため、どのアーカイバとも同様に、意図的に細工された「圧縮爆弾」は展開時にディスクを埋め尽くす可能性があります。それが問題になる場合は、未知のアーカイブをまず t でテストしてください。

10.3 安全な作成と正直なエラー

  • アーカイブは name.nik.tmp に書き込まれ、完了したときにのみ名前が変更されます。ガードが失敗時に一時ファイルを削除するため、中断された実行が中途半端に書かれたアーカイブや置き換えられたアーカイブを残すことはありません。
  • アーカイブ中にファイルが短くなった場合、nikpak は不整合なエントリを書き込む代わりに明示的なメッセージで中止します。読み取り不能なファイル、シンボリックリンク、特殊ファイルは警告付きでスキップされ (終了コード 1)、アーカイブが自分に追加されることはありません。
  • エラーはスクリプトが対応できるように分類されます。アーカイブ内のチェックサムまたはフレームエラーは破損 (終了コード 3)、認証失敗は誤ったパスワードまたは改ざん (終了コード 11)、拒否された書き込みは致命的エラー (終了コード 2) です。

  • nikpak -m5 はどのセットでも最小です。 7-Zip -mx9 に対して 2.4〜31.7 % 小さく、RAR 7 -m5 に対して 10.8〜38.4 %、ZIP -9 に対して 19.9〜60.4 % 小さくなります。録音音声では、NAC は LZ ベースの圧縮器が一致させることしかできないものを予測します。24 ビット音楽では 7-Zip が 12 %、nikpak が 37 % 節約します。

  • ZIP は高速だが、どこでも最大。 nikpak -m2 でもすべてのセットで ZIP -9 を上回ります。ZIP は小さなメディアアーカイブを nikpak -m2 より速く作成します。Deflate は NAC コーデックよりはるかに少ない作業で済むためですが、テキスト、Office ファイル、ソースコードでは遅くなります。
  • 展開。 一般セットは 0.9 秒 (nikpak -m2) または 5.6 秒 (-m5) で展開され、7-Zip は 6.0 秒、RAR は 6.7 秒、ZIP は 6.9 秒です。Deflate ストリームを再圧縮したアーカイブは、すべてのストリームが再構築されるため展開が遅くなります (Office セットで 0.7 秒 対 2.1 秒)。
  • このマシンでの RAR。 RAR はここでは 11.3 節より遅かったです (同程度のソースコードで -m5 -s が 27 秒ではなく 72 秒)。マシンとデータが異なるため、2 つの節を混ぜるべきではありません。この実行内では、すべてのツールが同じ条件でした。

これが nikpak にとって何を意味するか

最高レベルでは、nikpak は測定したすべてのセットで 4 つのツールの中で最小のアーカイブを作り、7-Zip -mx9 より 2.4〜31.7 % 小さくなります。代償は速度です。-m5 は時間と引き換えにサイズを得ます。上記の数値はすべてのツールを 1 コアに固定したものです。実際の使用では -m5 アーカイブはブロックをコア全体に分散します (4.5 節)。より高速な最高レベルはロードマップに残っています (15.2 節)。

12.3 耐量子性を大局的に見る

nikpak と RAR5 はどちらも 256 ビットの対称鍵で暗号化するため、両方とも Shor のアルゴリズムの影響を受けず、Grover のアルゴリズムに対しても約 128 ビットのセキュリティを保ちます。この点では両者を区別できません。nikpak がさらに加えるのは、メモリハードなパスワード処理 (現実世界で支配的な攻撃であるパスワード推測をはるかに高コストにする) と認証付き暗号 (改ざんを検出可能にする) です。また、公開鍵プリミティブがアーカイブ形式の一部になることは決してないという前提で最初から設計されており、公開鍵共有が追加された場合にはハイブリッドな耐量子方式を採用することがロードマップで約束されています。

12.4 どちらを選ぶべきか

  • nikpak を選ぶ のは、サイズと速度が重要な音声、画像、トラッカーミュージック、ソースコードのアーカイブ、スクリプトによるバックアップ、強力な既定の暗号化、オープンで文書化された形式に価値がある場合です。
  • RAR を選ぶのは、リカバリレコード、その場での更新が必要な場合、または RAR ツールしか持たない人とアーカイブを交換しなければならない場合です。
  • 両方を使う: 大量のメディアと暗号化バックアップには nikpak を使い、配布用には RAR を残すというワークフローを妨げるものは何もありません。

12.5 7-Zip と ZIP は?

11.7 節では nikpak 1.2 を 7-Zip 23.01 と Info-ZIP 3.0 とも比較しています。要約すると:

  • 最小のアーカイブには nikpak -m5 を選んでください。 測定したすべてのセットで 7-Zip -mx9 より 2.4〜31.7 % 小さくなります。Office ファイルで 31.7 %、テキストで 15.9 %、ソースコードで 2.4 % です。高速なバックアップには nikpak -m2 を選んでください (ソースコードで 7-Zip の既定より 56 倍高速)。nikpak の暗号化もより強力です。7-Zip は AES-256 とメモリハードでない SHA-256 鍵導出を使用し、-mhe を付けないとファイル名を隠しません。
  • 7-Zip を選ぶ のは、最高レベルで時間がより重要な場合 (大規模な Office やソースコードのセットでは高速)、既定レベルで文書を小さくしたい場合、または 7-Zip が読める多数の形式を開く必要がある場合です。
  • ZIP を選ぶ のは互換性のためだけです。どのオペレーティングシステムでも追加ソフトなしで開けますが、nikpak -m5 は 19.9〜60.4 % 小さく、ZIP の従来の暗号化は弱いです。

13 ビルド、配備、統合

13.1 PowerShell を使った Windows

nikpak は Rust で書かれ、Cargo でビルドされます。Windows では Rust に C/C++ リンカーが必要で、それは Visual Studio Build Tools に含まれます。管理者 PowerShell で両方を一度インストールし、PowerShell を開き直してください:

winget install Rustlang.Rustup
$o = '--wait --passive --add Microsoft.VisualStudio.Workload.VCTools'
$o += ' --includeRecommended'
winget install Microsoft.VisualStudio.2022.BuildTools --override $o



winget が利用できない場合は、rustup.rs から Rust を、Build Tools for Visual Studio を Desktop development with C++ ワークロード付きでインストールしてください。その後、ソースを含むフォルダーで:

.\build.ps1 # builds dist\nikpak.exe and dist\unNik.exe
.\build.ps1 -Test # runs the unit tests first


# if PowerShell refuses to run scripts:
powershell -ExecutionPolicy Bypass -File .\build.ps1



build.ps1 は Cargo がインストールされていることを確認し (ない場合はインストール方法を表示)、ビルドを実行し、失敗した場合は通常の原因を説明し、実行ファイルを dist\nikpak.exe にコピーします。

Windows インストーラー

.uild.ps1 -Installer (または npm run installer) は、Inno Setup 6.3 以降でセットアッププログラム dist\nikpak--setup.exe もビルドします (一度 winget install JRSoftware.InnoSetup でインストールしてください)。スクリプトは installer\nikpak.iss で、バージョンは Cargo.toml から取得されます。このセットアップファイルがシェアウェアサイトやダウンロードサイトにアップロードされます。

  • 既定では現在のユーザーのみに、管理者権限や UAC プロンプトなしで、%LOCALAPPDATA%\Programs\NikPak にインストールします。最初のページで「install for all users」(Program Files、管理者権限が必要) を提供します。

  • ショートカット: スタートメニューに NikPak、unNik、ライセンス。デスクトップに NikPak (常時) と、オプションでデスクトップに unNik。
  • .nik ファイルは常に登録されます (1.5.2 以降)。独自のアイコン (nikfile.ico、.zip ファイルのようなファスナー付きのページ)、種類名「NikPak archive」が付き、ダブルクリックで unNik で開きます (右クリックメニューの「Open with unNik」)。unNik は「プログラムから開く」と既定のアプリにも表示されます。アンインストーラーは登録を削除します。.nik ファイルが既に別のプログラムで開くよう設定されている場合、Windows は「プログラムから開く」で unNik を一度選ぶまでその選択を保持します。
  • 最後の「Launch NikPak」は通常ユーザーとして NikPak を起動し、決して管理者としては起動しないため、ドラッグ&ドロップが機能します。更新は以前のバージョンに上書きインストールされます (AppId 固定)。%APPDATA%\nikpak のライセンスは更新とアンインストールでも保持されます。セットアップにキーやキーファイルが含まれることはありません。
  • インストーラーは Windows に従って英語またはフランス語で動作します。公開前に、nikpak.exe とセットアップにコード署名証明書で署名し、Windows SmartScreen が不明な発行元について警告しないようにしてください。

buildall.ps1 は公開されるすべてを 1 回の実行でビルドし (nikpak.exe、unNik.exe、2 つのセットアップ、SHA256SUMS.txt)、binaries\ にコピーし、Web サイトを再ビルドして FTP でアップロードします (-NoUpload でアップロードをスキップ)。2 つ目のセットアップ unnik--setup.exe (installer\unnik.iss) は無料のアーカイブブラウザー unNik のみをインストールし、NikPak が既にインストールされている場合はプログラムのみをインストールするため、メニューが二重になることはありません。

13.2 npm を使ったビルド

Rust プロジェクトは npm を使わないため、npm は決して必須ではありません。便宜上、プロジェクトには Cargo を呼ぶだけのスクリプトを持つ小さな package.json が含まれており、Node.js のワークフローに慣れた開発者が使い慣れたコマンドを入力できます:

npm run build # cargo build --release
npm run dist # build.ps1 -> dist\nikpak.exe
npm test # cargo test --release
npm run clean # cargo clean



13.3 自己完結型の実行ファイル

.cargo/config.toml ファイルは、Windows の MSVC ターゲット向けに C ランタイムを静的リンクします。その結果得られる nikpak.exe (グラフィカルインターフェース付きで数 MB、なしで約 2.3 MB) は DLL 依存関係がなく、実行するマシンに Visual C++ Redistributable を必要としません。どこでも使うには PATH の通ったフォルダーにコピーしてください。リリースプロファイルは、小さく高速なバイナリのために完全最適化、リンク時最適化、単一コード生成ユニット、シンボル除去、panic = abort を有効にします。

13.4 macOS と Linux

./build.sh # builds and copies the result to dist/nikpak
# or: cargo build --release
sudo cp dist/nikpak /usr/local/bin/



macOS では最初にコマンドラインツールをインストールし (xcode-select --install)、Debian または Ubuntu では C コンパイラーをインストールします (sudo apt install build-essential)。Rust 自体は curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh で入手します。圧縮ライブラリは Cargo が C ソースからコンパイルするため、システムライブラリは不要です。

サイトの macOS 版と Linux 版のダウンロードは ./package-unix.sh が作成します。これは nikpak と unNik をビルドし、install.sh とともに binaries\nikpak--macos.zip (ユニバーサルバイナリ: Intel + Apple silicon) または binaries\nikpak--linux-.tar.gz にまとめます。Linux で ZIG=1 を設定すると、glibc 2.28 に対して cargo-zigbuild でビルドし、古いディストリビューションでも動作します。

13.5 依存関係

13.6 スクリプト

予測可能な終了コードと環境変数によるパスワードにより、nikpak はスクリプト化が容易です。警告を許容し、それ以上を失敗として扱う PowerShell バックアップ:

$archive = "D:\Backups\docs-$(Get-Date -Format yyyy-MM-dd).nik"
# the password comes from a file or secret store, not from the script
$env:NIKPAK_PASSWORD = Get-Content "$env:USERPROFILE\.nikpak-secret"


nikpak a -p -m3 -inul $archive "$env:USERPROFILE\Documents"
if ($LASTEXITCODE -gt 1) { throw "nikpak failed: $LASTEXITCODE" }


nikpak t -inul $archive # verify what was written
if ($LASTEXITCODE -ne 0) { throw "archive verification failed" }



シェルスクリプトでの同じ処理。ベア一覧コマンドを使って他のツールに渡します:

export NIKPAK_PASSWORD="$(cat ~/.nikpak-secret)"
nikpak a -p -m3 -inul "backup-$(date +%F).nik" ~/Documents || [ $? -eq 1 ]
nikpak lb backup-2026-10-16.nik | grep -i '\.wav$'



13.7 Total Commander

3.6 節で説明した統合は、nikpak が RAR の構文に従うことに依存しています。簡単なチェックリスト: 拡張子 nik を登録する。圧縮には a、展開には x を使う。長いファイルリストにはフロントエンドに @listfile を渡させる。無人展開には -o+ または -y を付ける。パスワードは -p または NIKPAK_PASSWORD 変数で渡す。グラフィカルなフロントエンドには問い合わせるコンソールがないためです。
