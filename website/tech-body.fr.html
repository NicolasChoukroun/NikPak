1 Introduction

nikpak est un archiveur en ligne de commande pour le format .nik. Il a été conçu autour de quatre idées : compresser mieux que les outils établis, le faire plus vite, protéger les données avec une cryptographie moderne, et fonctionner à l'identique sur Windows, macOS et Linux sous la forme d'un seul petit exécutable.

1.1 Objectifs de conception

  • Compact. Battre RAR 7 sur les données que les gens archivent réellement en masse. L'audio, les images et la musique tracker sont détectés par leur contenu et compressés avec des codecs sans perte spécialisés ; tout le reste utilise un flux Zstandard réglé et multi-thread.
  • Rapide. La compression et l'extraction doivent être limitées par le disque, pas par le processeur. À son niveau rapide -m2, nikpak archive environ 200 MB de fichiers source en moins d'une seconde sur un seul cœur.
  • Sûr. Chiffrement authentifié avec une fonction de dérivation de clé à coût mémoire élevé, noms de fichiers toujours masqués, altération toujours détectée, et un extracteur qui ne peut pas être amené à écrire en dehors de son dossier de destination.
  • Résistant au quantique. Seule une cryptographie symétrique de 256 bits est utilisée. Il n'y a ni RSA, ni courbe elliptique, ni code Diffie-Hellman nulle part dans nikpak, donc l'algorithme de Shor n'a rien à casser.
  • Portable et scriptable. Un seul exécutable lié statiquement, une ligne de commande compatible RAR, des codes de sortie prévisibles, et un -help qui documente chaque option.

1.3 À qui s'adresse-t-il ?

nikpak s'adresse à ceux qui archivent de grandes quantités de médias ou de code source et qui attachent de l'importance à la taille et à la vitesse, aux développeurs qui veulent un archiveur scriptable avec des codes de sortie sains et un format documenté, et à quiconque a besoin d'un chiffrement fort sans faire confiance à une implémentation fermée. Comme la ligne de commande suit les conventions de RAR, des frontaux tels que Total Commander peuvent le piloter avec peu ou pas de reconfiguration.

3 Référence de la ligne de commande

nikpak suit la syntaxe que connaissent les utilisateurs de RAR : nikpak [options] [files...]. Les options peuvent apparaître n'importe où, avant le nom de l'archive ou après ; -- met fin à l'analyse des options.

3.3 Les mots de passe en détail

Lorsqu'une archive est créée avec -p, nikpak résout le mot de passe dans cet ordre, et n'échoue jamais simplement parce qu'aucun n'a été fourni :

  • -p ou -P sur la ligne de commande : utilisé tel quel (8 caractères minimum).
  • La variable d'environnement NIKPAK_PASSWORD, qui garde le mot de passe hors de la liste des processus.
  • Une invite interactive, demandée deux fois pour confirmation. Une saisie vide génère un mot de passe aléatoire.
  • Sans terminal (par exemple dans une interface graphique), un mot de passe transmis via stdin ; s'il n'y en a aucun, un mot de passe aléatoire est généré.

Un mot de passe généré comporte 24 caractères issus d'un alphabet de 56 symboles sans ambiguïté (pas de 0/O, 1/l/I), soit environ 139 bits d'entropie. Il est affiché une fois dans un encadré sur la console. Il n'y a aucune récupération : une archive dont le mot de passe est perdu ne peut être ouverte par personne.

À l'ouverture d'une archive chiffrée, nikpak utilise les mêmes sources puis échoue avec le code de sortie 11 et un message explicatif ; il ne génère jamais rien, car un mot de passe généré ne pourrait pas correspondre.

3.5 Exemples

nikpak a backup.nik C:\Docs\*.txt Photos\ # create an archive
nikpak a -m5 -mt8 big.nik Projects\ # maximum, 8 threads
nikpak a -p secret.nik Taxes2026\ # encrypted, prompts
nikpak a -pMyLongPassw0rd s.nik f.pdf # password given
nikpak x backup.nik C:\Restore\ # extract with paths
nikpak e backup.nik *.jpg C:\Pics\ # only *.jpg, flat
nikpak x backup.nik Docs/report.pdf # extract ONE file
nikpak e backup.nik Docs/report.pdf -d C:\Out # one file, no path
nikpak x backup.nik Photos -d C:\Restore # one folder
nikpak l backup.nik *.pdf # list only PDFs
nikpak p backup.nik notes.txt # show a file
nikpak d backup.nik Temp *.bak # delete entries
nikpak l backup.nik # list
nikpak t secret.nik # test (asks password)
nikpak mt song.wav tracker.mod photo.bmp # which filter wins?



3.6 Intégration avec Total Commander et d'autres frontaux

Parce que nikpak accepte la syntaxe de commande de RAR (a, x, e, l, t, @listfile, -p, -ep1, -o+, -y, -m), un programme capable de piloter un rar.exe externe peut piloter nikpak.exe. Dans Total Commander, enregistrez l'extension nik sous Configuration, Archiveur, Programmes d'archive supplémentaires et pointez les commandes d'empaquetage et de dépaquetage vers nikpak.exe. Utilisez -o+ ou -y pour une extraction sans surveillance, car sans console nikpak ne peut pas demander s'il faut écraser et ignorera plutôt les fichiers existants. Les noms de menus diffèrent selon les versions de Total Commander ; consultez son aide intégrée pour les champs exacts.

Dossiers avec espaces sous Windows
Un chemin entre guillemets qui se termine par une barre oblique inverse, comme "C:\My Folder\", est mal analysé par Windows (le guillemet final est traité comme échappé). Pour les destinations avec espaces, utilisez plutôt -d "C:\My Folder".



3.7 L'interface graphique

nikpak lancé sans arguments, par exemple par un double-clic sur nikpak.exe, ouvre une petite fenêtre au lieu d'afficher son aide d'utilisation. Il fait une seule chose : compresser ce que vous y déposez.

  • Déposez un fichier ou un dossier, ou plusieurs à la fois, sur la fenêtre, ou cliquez sur le cercle (ou sur les liens choisir des fichiers / choisir un dossier) pour les sélectionner dans une boîte de dialogue ; un clic sur le cercle fait apparaître les deux boutons Choisir des fichiers et Choisir un dossier dans l'anneau. Ils sont compressés avec la meilleure compression (-m5) dans une archive nommée d'après le fichier (sans son extension), le dossier, ou, pour plusieurs éléments, le dossier dont ils proviennent. Une archive existante n'est jamais écrasée : report.nik devient report (2).nik.
  • La progression est affichée sous forme d'un grand pourcentage dans un cadran circulaire, avec la phase (analyse, compression, finition), la quantité traitée et le temps. Le bouton Annuler en dessous (ou la touche Échap) arrête immédiatement une longue compression et supprime l'archive inachevée ; la fenêtre reste ouverte pour la suivante. Fermer la fenêtre pendant une compression fait de même.
  • Terminé : l'anneau devient vert et affiche le nom de l'archive, sa taille par rapport à l'original et le temps. Afficher dans le dossier l'ouvre dans Explorer, Finder ou le gestionnaire de fichiers ; Compresser davantage (ou un clic sur le cercle) démarre la suivante.
  • Enregistrer dans : le dossier de destination en bas peut être saisi ou choisi avec Parcourir. Il est mémorisé pour la fois suivante (Windows : %APPDATA%\nikpak\settings.txt ; macOS : ~/Library/Application Support/nikpak ; Linux : ~/.config/nikpak). La première fois, c'est le Bureau.
  • Communauté : les trois boutons ronds en bas à droite ouvrent les pages Telegram, X et Discord de nikpak (section 1.5).
  • Passer à unNik : le bouton rond avec une flèche vers le haut, à gauche du bouton i, ferme NikPak et lance unNik (section 3.9). Après une compression, lui et le lien Ouvrir dans unNik sur l'écran de fin ouvrent immédiatement la nouvelle archive. Le bouton est désactivé pendant la compression.
  • Ouvrir le dossier de destination : le bouton de dossier entre le champ Enregistrer dans et Parcourir ouvre ce dossier dans Explorer ou Finder ; après une compression, il l'ouvre avec la nouvelle archive sélectionnée.
  • Sons : un clic doux pour les boutons, liens et options, et un son court pour chaque action (début du travail, succès, erreur, annulation, changement de programme, fichiers survolant la fenêtre). Ils sont produits par le programme lui-même, sans fichiers son. Le bouton haut-parleur dans la barre de titre les active et les désactive ; ils sont activés par défaut, et le choix est partagé avec unNik.
  • Langue : le bouton en bas à gauche, avec un drapeau et le nom de la langue dans sa propre langue, ouvre un menu des dix langues les plus parlées au monde (Ethnologue 2025) : English, 中文 (mandarin), हिन्दी (hindi), Español, العربية (arabe), Français, বাংলা (bengali), Português, Русский (russe) et Bahasa Indonesia. En choisir une l'enregistre et redémarre nikpak dans cette langue. La première fois, nikpak suit la langue de Windows (ou du système), sinon l'anglais. La ligne de commande reste en anglais.
  • Exécution en tant qu'administrateur : Windows ne permet pas de faire glisser des fichiers depuis Explorer vers un programme exécuté en tant qu'administrateur. Lorsque nikpak.exe est démarré en tant qu'administrateur (par exemple depuis un PowerShell administrateur), il se redémarre une fois en tant qu'utilisateur normal via Explorer afin que le glisser-déposer fonctionne. Si ce n'est pas possible, la fenêtre affiche un avis ; choisissez alors les fichiers avec les boutons.
  • État et À propos : en haut à gauche s'affichent EVALUATION COPY · REGISTER (un clic ouvre la boîte d'enregistrement) ou REGISTERED TO suivi du titulaire de licence. Le petit bouton i en haut à droite, à côté de réduire et fermer, ouvre la boîte À propos : version, © 2026 Nicolas Choukroun, distribué par Nikkoid LLC, le statut de licence, le site web et les conditions de licence (LICENSE.txt).

La fenêtre mesure 500 × 560 points (environ 9:10), de sorte qu'une capture d'écran de toute la fenêtre tient dans une publication d'image X (Twitter) sans recadrage. Elle est sans cadre : faites-la glisser par sa zone supérieure ; les boutons en haut à droite ouvrent la boîte À propos, la réduisent et la ferment. Lorsque nikpak.exe est démarré depuis Explorer, la fenêtre de console que Windows ouvre pour lui est fermée automatiquement ; démarré depuis une invite de commandes, l'invite est laissée telle quelle. Sans affichage graphique (par exemple via SSH), nikpak affiche son aide d'utilisation comme avant. L'interface utilise egui/eframe et intègre des sous-ensembles des polices Inter, Noto Sans SC, Noto Sans Devanagari, Noto Sans Bengali et Noto Sans Arabic (SIL Open Font License, voir assets/fonts/OFL.txt). Un exécutable en ligne de commande seule est compilé avec cargo build --release --no-default-features.

Le hindi, le bengali et l'arabe nécessitent une mise en forme : les lettres changent de forme et se joignent, les signes vocaliques se déplacent autour de leur consonne, et l'arabe s'écrit de droite à gauche. egui dessine un glyphe par caractère, ce qui afficherait ces langues de façon incorrecte ; nikpak ordonne donc ces textes avec l'algorithme bidirectionnel Unicode (unicode-bidi), les met en forme avec rustybuzz (un portage Rust de HarfBuzz), les rasterise avec ab_glyph et peint le résultat sous forme d'image (textshape.rs). Les mots latins et les nombres qu'ils contiennent conservent la police Inter. Les longues traductions sont réduites pour tenir dans leurs boutons, et les boîtes grandissent avec leur texte. Les traductions (i18n.rs) ont été écrites avec une assistance machine ; une relecture par des locuteurs natifs est la bienvenue.

3.12 Paquets : créer le paquet et ouvrir le paquet

Un paquet est un fichier .nik qui est un produit plutôt qu'une archive. Il réunit des fichiers et des dossiers, un nom, un auteur, une description, une image de couverture, un mot de passe et un contrat de licence utilisateur final dans un seul fichier qui peut être remis à un client ou vendu. C'est l'équivalent NikPak de la banque de sons Nikkosynth : la même forme, un nombre magique différent, de sorte qu'un paquet ne s'importe jamais dans Nikkosynth et qu'une banque de sons ne s'ouvre jamais comme un paquet (section 5.7).

Les deux boîtes sont dans la fenêtre de NikPak ; unNik ouvre les paquets avec la seconde.

  • Créer le paquet — la pastille en haut de la fenêtre, dans la rangée avec Rapide / Moyen / Meilleur, § Mentions et ▣ Couverture. Une seule boîte demande tout : le nom du paquet, l'auteur, une description, le mot de passe deux fois, un EULA facultatif, une image de couverture carrée, le dossier de destination et les fichiers à empaqueter. Cliquez sur le cadre de l'image pour choisir une couverture (ou déposez une image sur la fenêtre), et choisissez des fichiers ou un dossier dans la boîte — ou déposez-les sur la fenêtre tant qu'elle est ouverte : une image devient la couverture, tout le reste est ajouté à la liste.
  • Mémorisés d'un lancement à l'autre — l'auteur, le texte de l'EULA avec sa case à cocher, ainsi que le dossier de destination sont conservés dans le fichier de paramètres (package_author, package_eula_on, package_dest, et package-eula.txt à côté d'eux), de sorte que le second paquet n'a besoin que d'un nom, de ses fichiers et d'un mot de passe.
  • Le fichier — <name>.nik dans le dossier de destination, ou <name> (2).nik quand ce nom est déjà pris. Le mot de passe est obligatoire : les fichiers, leurs noms et leurs tailles sont chiffrés avec lui et compressés avec Zstandard. À l'écriture du paquet, la fenêtre affiche son anneau vert habituel avec la taille avant et après.
  • Ouvrir le paquet — déposez un paquet sur NikPak ou sur unNik, ou ouvrez-le depuis le gestionnaire de fichiers. Avant que quoi que ce soit ne soit déchiffré, une boîte montre la couverture, le nom, l'auteur, le nombre de fichiers et la description ; puis l'EULA, qui doit être lu et approuvé avec J'approuve ; puis le mot de passe et le dossier de destination. La destination est le même dossier mémorisé que pour Créer le paquet.
  • Extraction — chaque fichier est écrit avec ses dossiers, son CRC32 est vérifié et les noms d'entrée dangereux sont refusés (section 10.1) ; le dossier de destination peut être ouvert une fois le travail terminé. Quand le paquet comporte un EULA, celui-ci est écrit dans le dossier sous le nom Terms of use.txt, de sorte que les conditions accompagnent les fichiers.
  • La même chose en ligne de commande — un paquet remis à nikpak est nommé au lieu d'être refusé : « This is a NikPak package (500 files, by …), not a NikPak archive. Open it with unNik or NikPak to unpack it. »
  • À ne pas confondre avec — une archive (chapitre 5) est un conteneur général, un paquet est un produit accompagné d'une licence, et une banque de sons Nikkosynth est une banque de patches. Les trois se distinguent par leurs huit premiers octets (section 5.7).

3.13 Volumes découpés et .exe auto-extractible

Depuis la 1.12, une archive peut être distribuée sous forme d’un jeu de volumes ou d’un unique .exe auto-extractible, à la manière que connaissent les utilisateurs de WinRAR. Les deux servent à la distribution — mettre une archive sur des disques, sous une limite de téléversement, ou entre les mains de quelqu’un qui n’a rien d’installé — et les deux ne sont disponibles que pour les copies enregistrées.

  • Volumes découpés. -v<size> (ou la pastille Split de la fenêtre) découpe le flux d’octets de l’archive en volumes de la taille donnée — 100 MB, 700 MB, 1 GB, 2 GB, 4.7 GB, ou un nombre saisi de mégaoctets ou de gigaoctets. Le premier volume est photos.nik, le suivant photos.n01, photos.n02 … Pour dépaqueter, extrayez le premier volume : le lecteur suit photos.n01, photos.n02 … de lui-même. Un volume rempli exactement reçoit un successeur vide, ce qui permet au lecteur de distinguer « un autre suit » de « dernier ».
  • Auto-extractible. -sfx écrit photos.exe — unNik avec l’archive ajoutée à la fin, plus un petit trailer. Quiconque l’exécute obtient une petite fenêtre (nom, taille, nombre de volumes, champ Extraire vers, mot de passe lorsque l’archive est chiffrée, conditions à approuver, un bouton Extraire) qui dépaquette sans rien d’installé et sans avoir besoin de nikpak. -v et -sfx ensemble donnent photos.exe plus photos.n01 …
  • Copies enregistrées uniquement. Les volumes découpés et le .exe sont les deux fonctionnalités qui font d’une archive une distribution ; une copie d’évaluation ne les écrit donc pas. La pastille Split ouvre à la place la boîte d’enregistrement, et -v / -sfx sont refusés sur la ligne de commande avant que quoi que ce soit ne soit écrit.
  • Déposez une archive pour l’extraire. Depuis la 1.13.1, un .nik déposé sur la fenêtre — ou n’importe quel volume d’un jeu découpé, ou un .exe auto-extractible — ouvre la boîte Extraire (nom, taille, volumes, mot de passe, destination) au lieu de le compresser.

4 Architecture

nikpak est un programme Rust unique d'environ 9 600 lignes (tests unitaires compris) réparties sur seize fichiers source, plus l'outil privé de licence nikpak-keygen. Sa règle de conception centrale est le flux continu : les fichiers sont lus par morceaux de 256 KiB, poussés à travers une chaîne d'écrivains, et jamais conservés en mémoire en entier (les seules exceptions sont les données de pixels BMP, limitées à 256 MiB, et les tampons de travail de 64 KiB des codecs).

4.3 Créer une archive, étape par étape

  • Validez l'emplacement de sortie. Une archive existante n'est remplacée qu'avec -o+ (ou un oui interactif) ; sinon nikpak explique que l'ajout n'est pas pris en charge.
  • Collectez l'entrée : les caractères génériques sont développés (PowerShell ne le fait pas), les @listfiles sont lus, les exclusions appliquées, les liens symboliques et les fichiers spéciaux ignorés avec un avertissement, et l'archive elle-même n'est jamais ajoutée à elle-même.
  • Résolvez le mot de passe si le chiffrement a été demandé (section 3.3) et dérivez la clé avec Argon2id.
  • Écrivez l'en-tête, puis construisez la chaîne d'écrivains : fichier, écrivain tamponné, chiffreur de blocs optionnel, encodeur Zstandard.
  • Écrivez chaque entrée. Les fichiers média passent par la détection et l'essai (chapitre 7) ; tout le reste est copié par morceaux de 256 KiB pendant qu'un CRC32 est calculé.
  • Écrivez le marqueur de fin avec le nombre d'entrées, terminez la trame Zstandard, scellez le dernier bloc chiffré et videz vers le disque.
  • Renommez name.nik.tmp en name.nik. Si quelque chose échoue avant, un objet garde-fou supprime le fichier temporaire, de sorte qu'une archive à moitié écrite ne remplace jamais une bonne archive.

4.4 Extraire une archive, étape par étape

  • Lisez et validez l'en-tête : nombre magique, version, drapeaux, méthode et, pour les archives chiffrées, les paramètres Argon2id, qui sont vérifiés en plage avant toute allocation de mémoire.
  • Obtenez le mot de passe et dérivez la clé. Le premier bloc authentifié prouve ou réfute alors le mot de passe.
  • Parcourez le flux d'entrées. Chaque nom d'entrée est assaini (section 10.1) avant tout accès au système de fichiers.
  • Écrivez les fichiers avec create_new, définissez les horodatages et les permissions, et vérifiez le CRC32 des octets reconstruits. Un fichier dont le CRC échoue est supprimé plutôt que conservé.
  • Vérifiez la fin de l'archive : après le marqueur de fin, le flux doit réellement se terminer et, si chiffré, le dernier bloc authentifié doit avoir été traité. Cela détecte la troncature et les données ajoutées.

4.5 Mémoire et threads

Zstandard utilise des threads de travail pour la compression (tous les cœurs par défaut, -mt<N> pour limiter). Depuis la 1.13, le niveau maximal s’exécute aussi en parallèle : -m5 découpe les entrées binaires et texte en blocs équilibrés — un par cœur, jamais plus petits que 8 MiB — et compresse chaque bloc sur son propre thread, tandis que le travail par fichier (essais média, recompression Deflate) s’exécute sur un pool de threads de travail à chaque niveau. La mémoire de l’encodeur est bornée par ENCODER_RAM_BUDGET (1.5 GiB) : plus de blocs signifie un dictionnaire LZMA2/PPMd plus petit. NIKPAK_SEQ=1 restaure le chemin un-à-la-fois. La décompression, le codec audio et le chiffrement s’exécutent sur le thread appelant ; Argon2id a besoin de 64 MiB pour la dérivation de clé, et les niveaux les plus élevés utilisent une fenêtre de correspondance de 128 MiB.

Un fichier .nik est un petit en-tête fixe suivi d'un corps. Le corps est un unique flux solide : toutes les entrées sont concaténées, compressées ensemble, et éventuellement chiffrées. La version 2 du format ajoute les enregistrements média ; les archives de version 1 restent lisibles.

L'en-tête complet (12 octets, ou 59 octets quand l'archive est chiffrée, plus la déclaration légale et la couverture quand elles sont présentes) est ensuite authentifié comme donnée associée de chaque bloc chiffré : il ne peut pas être modifié sans que cela se voie.

Déclaration légale (bit 1 des drapeaux). Après les champs fixes viennent une longueur sur 4 octets et la déclaration en UTF-8, 64 Ko au plus. Elle est en clair pour qu'un programme puisse l'afficher avant de demander le mot de passe, et nikpak refuse de lister, tester, extraire ou supprimer quoi que ce soit tant qu'elle n'a pas été acceptée : dans une fenêtre avec J'approuve, en console en tapant YES, ou avec -accept. Un lecteur qui ne connaît pas le bit 1 refuse l'archive : la déclaration ne peut pas être contournée avec une version plus ancienne.

Couverture (bit 2 des drapeaux). Puis une longueur sur 4 octets et une image JPEG ou PNG, 4 Mo au plus ; nikpak la fabrique à partir de n'importe quelle image, recadrée en carré et mise à l'échelle 1024 x 1024. Elle se lit sans le mot de passe et s'affiche dans unNik et Nikkomander.

Les deux font partie de l'en-tête : dans une archive chiffrée, elles sont authentifiées avec chaque bloc, et modifier ou retirer les conditions ou la couverture empêche l'archive de s'ouvrir. Les archives qui n'en ont pas sont écrites exactement comme avant.

5.2 Enregistrements d'entrée

À l'intérieur du flux (déchiffré, décompressé), chaque entrée est un enregistrement. Tous les entiers sont petit-boutistes.

5.3 Découpage du corps chiffré

Lorsque le drapeau de chiffrement est activé, la sortie zstd est découpée en blocs de 64 KiB de texte en clair. Chaque bloc est stocké sous forme d'une longueur 32 bits gros-boutiste suivie du texte chiffré, qui fait 16 octets de plus à cause de l'étiquette Poly1305. Un bloc n'est scellé que lorsqu'au moins un octet de plus suit, de sorte que le dernier bloc n'est jamais vide et peut être marqué comme final (section 8.3).

5.4 Pourquoi un flux solide ?

Compresser tous les fichiers en un seul flux permet au compresseur de trouver des répétitions entre fichiers, ce qui compte énormément pour les arborescences de sources et les collections de documents (le benchmark du chapitre 11 montre que la sortie non solide de RAR est presque deux fois plus grande que sa sortie solide sur 10 949 fichiers). Le prix à payer est l'accès séquentiel : extraire un seul fichier exige de décompresser ce qui le précède. nikpak réduit ce coût pour les entrées média en les sautant sans les décoder.

5.5 Versionnage

L'octet de version est comparé à la version la plus élevée que le programme comprend. Une archive plus récente produit le message Version d'archive non prise en charge N ; veuillez mettre à jour nikpak plutôt qu'une erreur de corruption trompeuse. Les drapeaux, méthodes ou filtres média inconnus sont rejetés de la même manière.

5.6 Corps multi-moteur (version 3)

Les archives créées avec -m5 utilisent la méthode 2. Le flux d'enregistrements interne décrit en 5.2 est inchangé, mais il est découpé, uniquement entre les entrées, en blocs, et chaque bloc est compressé avec son propre moteur. Mis bout à bout, les blocs décompressés sont exactement le flux d'enregistrements d'une archive à moteur unique, de sorte que le listage, le test et l'extraction fonctionnent de la même façon.

Lorsqu'il est chiffré, le corps est protégé par les mêmes blocs authentifiés que toute autre archive (chapitre 8).

5.7 Le conteneur de paquet (NIKPACK2)

Outre les archives (ce chapitre) et les banques de sons Nikkosynth, un .nik peut être un paquet NikPak (section 3.12). Les trois partagent l'extension, c'est pourquoi chaque programme identifie un fichier par ses huit premiers octets :

Kind First eight bytes Written by
Archive NikPak 89 4E 49 4B 0D 0A 1A 0Anikpak ; unNik la lit (chapitre 5)
Paquet NikPak NIKPACK2 (4E 49 4B 50 41 43 4B 32)NikPak 1.11 et ultérieur ; unNik le dépaquette
Nikkosynth soundbank NIKPACK1 (4E 49 4B 50 41 43 4B 31)Nikkosynth uniquement

Un paquet et une banque de sons sont construits de la même façon — une ligne d'en-tête JSON en clair, puis un corps scellé — mais c'est le nombre magique différent qui sépare les deux produits.

L'en-tête est une seule ligne JSON, délibérément lisible sans le mot de passe : c'est ce que la boîte Ouvrir le paquet affiche avant de demander celui-ci. Il porte format (« nikpak-package »), version (1), name, author, description, eula, cover (base64 d'un JPEG ou PNG de 1024 × 1024) avec coverType, count, encrypted et, quand le paquet est chiffré, le salt et le nonce de 16 octets en hexadécimal. Aucune information sur les fichiers n'y figure : leurs noms et leurs contenus sont à l'intérieur du corps. Comme l'en-tête fait partie de ce que couvre l'étiquette, un paquet dont l'EULA a été modifié ou supprimé ne s'ouvre plus.

Le corps est le flux d'enregistrements de la section 5.2 — les mêmes enregistrements 1 FILE, 2 DIR et 0 END, avec des tailles sur 64 bits, le mtime, le mode et un CRC32 par fichier — compressé en un seul flux Zstandard (niveau 19). Un paquet n'a pas d'enregistrements MEDIA ni de recompression Deflate : ses fichiers sont stockés tels quels et tout le flux est compressé une seule fois, ce qui garde le format assez petit pour que les deux produits puissent l'implémenter.

  • Clé — SHA-256 itéré 600 000 fois sur salt ‖ mot de passe, scindé en une clé de chiffrement de 32 octets et une clé de vérification de 32 octets. Une demi-seconde par essai, ce qui rend coûteuse l'attaque d'un paquet volé.
  • Corps — XOR avec le flux de clés SHA-256(clé de chiffrement ‖ nonce ‖ compteur), 32 octets à la fois.
  • Étiquette — HMAC-SHA-256 sur la ligne d'en-tête et le texte chiffré, 32 octets à la fin, comparés en temps constant. Un mauvais mot de passe et un fichier endommagé échouent de la même façon, si bien qu'on ne peut pas les distinguer l'un de l'autre.
  • Pourquoi pas Argon2id et XChaCha20-Poly1305 — parce qu'un paquet est un format partagé : c'est la même construction que celle des banques de Nikkosynth, et les deux produits doivent pouvoir l'implémenter en quelques dizaines de lignes de code de bibliothèque standard. C'est un conteneur scellé — un seul écrivain, un seul lecteur, aucun message choisi par l'attaquant, le mot de passe ne circule jamais — et c'est ce qu'il doit être.

Limites : description 4 Ko, EULA 64 Ko, auteur 256 octets, nom du paquet 256 octets, couverture 4 Mo, nom d'entrée 4096 octets, corps 512 Mo après décompression (annexe A).

5.8 Volumes découpés et le trailer SFX

Un jeu découpé n’est pas un second format : les volumes sont le propre flux d’octets de l’archive coupé aux frontières de taille. Rien dans le format ne connaît le découpage, à part un drapeau d’en-tête. Le premier volume est l’archive elle-même — un .nik complet dont l’en-tête porte la taille de volume — et les autres sont de simples continuations.

En-tête. Bit de drapeau 3 (FLAG_SPLIT) plus une taille de volume sur 64 bits après la couverture. La taille de volume fait partie de l’AAD lorsque l’archive est chiffrée, et c’est elle qui permet au lecteur de dire « l’archive continue dans photos.n01, qui manque » au lieu de « archive tronquée » lorsqu’un volume est perdu. Les anciens lecteurs refusent l’archive, ce qui est correct : sans la taille, un jeu ressemble à un fichier endommagé.

Le lecteur Chain. split::Chain est un Read qui commence au début du premier volume (ou à un décalage à l’intérieur d’un .exe) et qui, en atteignant la fin d’un volume, ouvre le suivant (photos.n01, photos.n02, …, puis .100 …) et continue. Chaque chemin de lecture du programme passe par lui, de sorte que la liste, la consultation, l’extraction et le menu contextuel lisent tous chaque volume d’un jeu.

L’écrivain Out. split::Out est l’écrivain derrière -v et -sfx. Il écrit des fichiers ….tmp et les renomme dans finish(), de sorte qu’une exécution échouée ne laisse jamais un demi-volume. Il écrit un fichier, un jeu de volumes, ou un .exe.

Auto-extractible. Un .exe est les octets de unNik.exe suivis des octets de l’archive et d’un trailer de 40 octets — le nombre magique NIKPAKSFX, le décalage et la longueur de l’archive, la taille totale et un CRC32. unNik cherche ce trailer dans son propre exécutable au démarrage et, lorsqu’il en trouve un, affiche une petite boîte au lieu de la fenêtre de dépôt. Le .exe fait environ 8 MB plus l’archive.

6 Le moteur de compression

6.1 Pourquoi Zstandard

Zstandard combine la correspondance LZ77 avec un étage d'entropie construit à partir du codage de Huffman et de l'entropie à états finis (FSE). Comparé à l'algorithme Deflate de ZIP, il trouve des correspondances sur une fenêtre bien plus grande, modélise les littéraux et les longueurs de correspondance avec des codes d'entropie plus serrés, et décode à des gigaoctets par seconde. C'est aussi un format ouvert et largement audité, ce qui garde les données de nikpak récupérables par des outils indépendants.

6.2 Correspondance des niveaux

nikpak accepte à la fois les niveaux de style RAR (-m0 .. -m5) et les niveaux de style zip (-0 .. -9) et les fait correspondre aux niveaux Zstandard :

OptionNiveau ZstandardCaractère

-m1 1Le plus rapide
-m2 3Rapide ; environ 0.9 s pour 197 MB sur un cœur (valeur par défaut jusqu'à la 1.2.0)
-m3 9Bon équilibre
-m4 15Élevé ; fenêtre de 128 MiB et correspondance longue distance ; recompression Deflate (7.9)
-m5 (default)LZMA2 / PPMdMaximal, et valeur par défaut depuis 1.2.1 : corps multi-moteur (6.7) et recompression Deflate



Les niveaux de style zip correspondent comme suit : -0 stocke, -1 à -6 utilisent Zstandard 1 à 6, -7 utilise 9, -8 utilise 12 et -9 équivaut à -m5.

6.3 Grande fenêtre et correspondance longue distance

Au niveau Zstandard 15 et au-delà, nikpak active une fenêtre de correspondance de 2^27 octets (128 MiB) et la correspondance longue distance. Les arborescences de sources, les jeux de documents et les sauvegardes contiennent de nombreux fichiers presque identiques qui se trouvent loin les uns des autres dans le flux ; une fenêtre normale de 8 MiB ne peut pas voir au-delà. Sur le jeu de test de 197 MB, cela a réduit la sortie à -m5 de 26.3 MB à 24.4 MB et à -m4 de 29.5 MB à 26.8 MB, sans coût en vitesse pour -m4 et avec un petit coût pour -m5. Une fenêtre de 2^27 reste dans la limite de décodeur par défaut de Zstandard, donc tout décodeur standard peut lire les données.

6.4 Multi-threading

L’encodeur découpe l’entrée en tâches qui s’exécutent sur des threads de travail (tous les cœurs par défaut). La vitesse de compression évolue donc avec le nombre de cœurs, tandis que le format reste un flux unique. Depuis la 1.13, -m5 découpe en plus l’archive en un bloc par cœur et compresse les blocs en parallèle (section 4.5) ; le pipeline par fichier s’exécute à chaque niveau. Tous les chiffres de ce guide ont été mesurés sur un cœur ; sur une machine multi-cœurs typique, nikpak est considérablement plus rapide qu’indiqué.

6.5 Intégrité à l'intérieur du flux

La trame Zstandard porte sa propre somme de contrôle de contenu, nikpak ajoute un CRC32 par fichier et un marqueur de fin avec le nombre d'entrées. Une archive simple endommagée est donc détectée à trois niveaux : la somme de contrôle de trame, le CRC par fichier et le marqueur de fin.

6.6 Mode stockage

-m0 écrit les entrées sans compression. C'est utile pour les données déjà compressées, et c'est aussi le seul mode dans lequel les filtres média sont délibérément contournés : un utilisateur qui demande le stockage ne s'attend pas à ce que les données soient transformées.

6.7 Le niveau maximal : LZMA2 et PPMd

Zstandard est le bon moteur pour la vitesse, mais à ses réglages les plus forts il reste encore quelques pour cent derrière LZMA2 sur le code source et les documents, et bien derrière PPMd sur la prose. Depuis la version 1.2, -m5 construit donc l’archive à partir de blocs (format en 5.6) :

  • Bloc binaire. Les dossiers, les fichiers binaires, les entrées média et les entrées recompressées en Deflate sont compressés avec LZMA2 : préréglage 9, longueur agréable 273, profondeur de recherche de correspondance 32, et un dictionnaire dimensionné selon les données (1 à 128 MiB).
  • Bloc texte. Les fichiers dont les premiers 64 KiB ne contiennent aucun octet nul et presque aucun caractère de contrôle (code source, texte, CSV, HTML, XML ...) vont dans un second bloc. Quatre séries contiguës de 1 MiB de ces fichiers sont compressées à l'essai avec PPMd variante I (ordre 8, modèle de 192 MiB) et avec LZMA2 réglé pour le texte (lc 4, pb 0), et le plus petit résultat l'emporte. La prose favorise PPMd ; les grandes arborescences de sources avec de nombreux fichiers presque identiques favorisent LZMA2, car il peut copier de longues répétitions entre fichiers.
  • Ordre. Dans chaque bloc, les fichiers sont triés par extension, puis par nom de fichier, comme le fait 7-Zip, afin que les fichiers identiques ou similaires soient voisins. Avec l'échantillon d'essai contigu, cela a rendu le jeu de données général 7.5 % plus petit.

Les réglages LZMA2 « extrêmes » ont été mesurés et rejetés : sur du XML de tableur, ils étaient jusqu’à dix fois plus lents et pas plus petits. Depuis la 1.13, les blocs d’une archive -m5 sont compressés en parallèle, un par cœur ; -mt<N> fixe le nombre de blocs (2 pour le meilleur ratio, 8 pour la vitesse).

7 Intelligence des médias

Un compresseur généraliste voit des octets. Il ne sait pas qu'un fichier WAV est une forme d'onde dont l'échantillon suivant est prédictible à partir des précédents, ni que les pixels voisins d'une photographie sont presque égaux. La couche média de nikpak apporte ce savoir : elle reconnaît ces fichiers, applique une transformée sans perte qui expose la redondance, et laisse le compresseur (ou un codec dédié) l'exploiter. C'est là que nikpak gagne le plus face à RAR.

7.1 Détection par le contenu

La détection regarde les premiers octets de chaque fichier d'au moins 8 KiB et ne fait jamais confiance à l'extension, de sorte qu'un WAV renommé en .dat est toujours trouvé et qu'un fichier texte appelé .wav ne l'est pas.

7.2 L'essai : choisir le meilleur filtre par fichier

Aucune transformée unique n'est la meilleure pour chaque fichier. Le codage prédictif l'emporte sur la musique enregistrée ; la séparation en plans d'octets l'emporte sur l'audio issu d'une source compandée 8 bits (où seulement un millier de valeurs 16 bits distinctes apparaissent) ; la compression simple l'emporte sur le silence et les échantillons tracker très répétitifs. nikpak mesure donc au lieu de deviner.

  • Prélevez un échantillon : toute la région d'échantillons lorsqu'elle fait jusqu'à 3 MiB, sinon trois fenêtres de 768 KiB à 5 %, 45 % et 85 % de l'audio. Pour les images, les premières lignes jusqu'à environ 4 MiB.
  • Compressez l'échantillon avec Zstandard simple au niveau 3 (la référence) et avec chaque filtre applicable : NAC, Shuffle et Shuffle+Delta pour l'audio 16/24/32 bits ; NAC et Shuffle+Delta pour l'audio 8 bits ; MED pour les images.
  • Gardez le filtre avec la plus petite estimation, mais seulement s'il bat la référence d'au moins 2 %. Sinon, le fichier est stocké avec une compression normale.
  • Écrivez le fichier avec le gagnant. Tout cela se produit par fichier, de sorte qu'une archive peut contenir des WAV codés avec des méthodes différentes à côté de fichiers ordinaires.

nikpak mt effectue la même mesure sur le fichier entier et affiche un tableau, ce qui est la façon dont le benchmark du chapitre 11 a été exploré. Dans les options, -mc- désactive les filtres et -mc+ force le filtre par défaut sans essai.

Sans perte, vérifié et contournable
Chaque filtre est exactement réversible. Le CRC32 stocké avec chaque entrée est calculé sur les octets d'origine et vérifié à l'extraction, l'encodeur NAC vérifie chaque bloc pendant l'écriture (section 7.4), et -mc- désactive toute la couche.



7.3 Le codec audio NAC

NAC (codec audio de nikpak) est un codec sans perte par blocs pour le PCM entier. Il appartient à la même famille que FLAC : prédiction linéaire suivie d'un codage de Rice. Il possède son propre flux de bits, conçu pour cette archive, et est utilisé pour WAV, AIFF et les données d'échantillons des fichiers MOD.

Blocs et décorrélation stéréo

L'audio est découpé en blocs de 4096 trames d'échantillons, chacun codé indépendamment, ce qui rend le codec robuste (une erreur ne peut pas se propager) et permet à l'encodeur de s'adapter au matériau changeant. Pour la stéréo, l'encodeur choisit l'une des quatre représentations par bloc :

1Gauche, Côté R = L - S

3Milieu, Côtésum = (M << 1) | (S & 1), L = (sum + S) >> 1, R = (sum - S) >> 1



avec Side = L - R et Mid = (L + R) >> 1. Le canal latéral a besoin d'un bit de plus qu'un canal normal et est codé avec bits + 1. Le mode est choisi à moindre coût : l'encodeur additionne les valeurs absolues du résidu du prédicteur fixe d'ordre 2 de L, R, M et S et prend la paire avec le plus petit total. Pour les enregistrements dont les canaux sont fortement corrélés, Milieu/Côté économise généralement plusieurs pour cent.

Prédicteurs fixes

order 0: e[i] = x[i]

Les premiers order échantillons d'un bloc sont stockés tels quels comme valeurs d'échauffement.

Codage prédictif linéaire (LPC)

Pour la musique tonale et harmonique, un prédicteur dont les coefficients sont ajustés au bloc est bien meilleur qu'un polynôme fixe. L'encodeur les calcule comme suit :

  • Appliquez une fenêtre de Tukey (atténuation sur le premier et le dernier quart) au bloc, afin que ses bords ne faussent pas les statistiques.
  • Calculez l'autocorrélation r[0..32] du signal fenêtré.
  • Exécutez la récursion de Levinson-Durbin, qui produit le jeu de coefficients optimal pour chaque ordre de 1 à 32 en une seule passe : k = (r[i] - sum a[j] r[i-j]) / err, a[i] = k, a[j] = a[j] - k a[i-j], err = err (1 - k^2).
  • Quantifiez les coefficients réels en entiers avec une précision de 12, 14 ou 15 bits (selon la largeur d'échantillon), en choisissant une échelle puissance de deux (shift, de 0 à 20) pour que le plus grand coefficient tienne juste. L'arrondi utilise un retour d'erreur, de sorte que les erreurs de quantification ne s'accumulent pas entre les coefficients.
  • Évaluez plusieurs ordres (l'ensemble dépend du niveau d'effort, ci-dessous), calculez le résidu de chacun, et gardez celui avec la plus petite taille totale estimée, y compris le coût d'envoi de ses coefficients.

Le prédicteur lui-même est de l'arithmétique entière pure, ce que le décodeur exécute :

pred[i] = (q[0]*x[i-1] + q[1]*x[i-2] + ... + q[n-1]*x[i-n]) >> shift
e[i] = x[i] - pred[i] (n = order; the sum uses 64 bits)



La virgule flottante n'est utilisée que par l'encodeur pour décider quels coefficients entiers envoyer. Le décodeur ne touche jamais à la virgule flottante, de sorte que le décodage est exact au bit près sur chaque processeur et chaque compilateur.

Codage des résidus

Les erreurs de prédiction sont mappées en nombres non signés avec la transformée en zigzag (u = (e << 1) XOR (e >> 63), de sorte que les petites valeurs positives et négatives deviennent de petits nombres) et codées avec des codes de Rice partitionnés. Le résidu d'un bloc est divisé en 2^p partitions (p de 0 à 8, choisi par l'encodeur) ; chaque partition reçoit son propre paramètre de Rice k (5 bits). Une valeur est écrite sous forme de u >> k en unaire (autant de zéros et un un) suivi des k bits bas. Le meilleur k d'une partition est dérivé de la somme de ses valeurs, de sorte que le coût de chaque prédicteur candidat peut être estimé à moindre coût à partir de sommes courantes au lieu de l'encoder.

Niveaux d'effort

Le niveau de l'archive (option -m) choisit combien d'ordres LPC sont essayés par bloc. Plus d'ordres signifient un résultat légèrement plus petit et un encodeur plus lent ; la vitesse du décodeur est la même.

Les prédicteurs fixes d'ordre 0 à 4 sont toujours essayés. Dans le benchmark, le niveau d'effort a changé le résultat de la musique stéréo de moins de 0.05 % : le grand gain vient du simple fait d'utiliser la prédiction.

7.4 Auto-vérification

Écrire une archive est la seule occasion de détecter un bug d'encodeur, donc l'encodeur NAC ne se fait pas confiance. Après avoir encodé chaque bloc, il décode à nouveau le bloc et compare le résultat aux échantillons d'origine. À la moindre différence, il ré-encode le bloc en verbatim (ce qui ne peut pas échouer) et vérifie à nouveau ; si même cela échoue, l'archivage s'arrête avec une erreur explicite et la suggestion d'utiliser -mc-. Le chemin de repli est exercé par les tests unitaires, qui forcent le codage verbatim pour chaque combinaison de profondeur de bits et de nombre de canaux, et le mécanisme transforme un éventuel bug silencieux de perte de données en une condition détectée et récupérable.

En plus de cela, le décodeur est fuzzé : des milliers de blocs d'octets aléatoires et de blocs avec des bits inversés lui sont soumis dans les tests unitaires, et il doit renvoyer une erreur sans paniquer ni allouer des quantités déraisonnables de mémoire. Pendant le développement, cela a trouvé un vrai bug (pour le matériau 32 bits, la recherche du paramètre de Rice pouvait revenir vide et retomber sur un paramètre qui aurait produit un code de plusieurs gigaoctets) ; il est corrigé et couvert par un test.

7.5 Shuffle et Shuffle+Delta

Certains audio ne réagissent pas à la prédiction. Les fichiers WAV de la galerie utilisés dans le benchmark sont en 16 bits, mais ne contiennent qu'environ un millier de valeurs d'échantillons distinctes, car ils proviennent d'une source compandée 8 bits. Un prédicteur ne peut pas l'exploiter, et FLAC les compresse à 84 % de l'original tandis que Zstandard simple a besoin de 63 %. Ce qui aide, c'est d'arranger les octets pour que le compresseur voie des données homogènes :

  • Shuffle sépare les octets des échantillons en plans : tous les octets de poids faible du canal 0, puis tous les octets de poids fort du canal 0, puis le canal 1, et ainsi de suite, par blocs de 32768 trames. Le plan d'octets hauts est lisse et le plan d'octets bas a un alphabet très restreint ; le codeur d'entropie de Zstandard modélise chacun bien mieux que le mélange entrelacé.
  • Shuffle+Delta remplace d'abord chaque échantillon par sa différence avec l'échantillon précédent du même canal (modulo la largeur d'échantillon, de sorte que c'est exactement réversible, avec un état reporté entre les blocs) puis mélange. Cela aide lorsque le signal est lisse mais pas assez prédictible pour que NAC gagne.

Sur les 35 fichiers de la galerie, l'archive avec le meilleur filtre par fichier (choisi par l'essai) fait 51 % de la taille d'origine à -m2 et 47 % à -m5, contre 63 % pour Zstandard simple.

7.6 Fichiers MOD ProTracker

Un module MOD est un en-tête de 1084 octets (titre, 31 descripteurs d'échantillons, une table d'ordre de motifs de 128 entrées et une signature de 4 octets au décalage 1080), puis les données de motifs, puis les échantillons bruts signés 8 bits de tous les instruments. nikpak calcule où les échantillons commencent et quelle est leur longueur :

patterns = max(order table) + 1
sample_start = 1084 + patterns * 256 * channels (4 ch: 1024 B per pattern)
sample_bytes = sum of (length in words * 2) over the 31 descriptors,
clamped to the end of the file



L'en-tête et les motifs sont stockés tels quels (le compresseur gère bien ces événements de notes répétitifs) et la zone d'échantillons est traitée comme un unique flux mono, signé, 8 bits pour l'essai. Par fichier, NAC, Shuffle+Delta ou la compression simple l'emporte : les instruments échantillonnés favorisent surtout NAC, tandis que sur certains modules (par exemple ceux avec des échantillons très courts ou très répétitifs), la compression simple gagne. Les modules tronqués sont gérés en ramenant la région aux données réellement présentes.

7.7 Images BMP

Un BMP non compressé stocke des lignes de pixels rembourrées jusqu'à un multiple de quatre octets. Le filtre fonctionne en quatre étapes :

  • Séparez la région de pixels en un plan par canal (B, V, R, et A pour 32 bits), en mémorisant séparément les octets de rembourrage par ligne.
  • Décorrélez la couleur. Soustrayez le plan vert des plans bleu et rouge (modulo 256). Dans les photographies, les trois canaux sont fortement corrélés, de sorte que les différences sont petites.
  • Prédisez chaque pixel à partir de ses voisins avec le prédicteur MED (détecteur médian de contours), celui utilisé par le codeur d'images LOCO-I : pour la gauche a, le dessus b et le dessus-gauche c, la prédiction est min(a,b) si c >= max(a,b), max(a,b) si c <= min(a,b), et a + b - c sinon. L'erreur de prédiction remplace le pixel (modulo 256). Sur les contours, le prédicteur suit le contour ; sur les dégradés lisses, il extrapole le dégradé.
  • Concaténez les plans de résidus et les octets de rembourrage et laissez Zstandard les compresser. Les régions lisses deviennent des suites d'octets proches de zéro.

Le décodeur inverse exactement les étapes. Les BMP 8 bits sautent l'étape de couleur ; l'essai décide alors si la prédiction aide pour cette palette, car prédire des indices de palette n'a de sens que pour les palettes en niveaux de gris ou ordonnées de façon lisse. Les fichiers BMP de plus de 256 MiB ne sont pas filtrés, afin de borner l'utilisation mémoire.

7.8 Pourquoi cela bat RAR

RAR compresse les médias avec son moteur général de correspondance et de Huffman plus un petit ensemble de filtres d'octets. nikpak, à la place, donne à l'audio un vrai codec prédictif avec décorrélation stéréo par bloc et codage de Rice adaptatif, donne aux images un vrai prédicteur 2-D avec décorrélation de couleur, et choisit par fichier par la mesure. La conséquence est visible dans le benchmark : 12 à 15 % plus petit sur l'audio de toute sorte, 13 % sur la musique tracker et 39 % sur les photographies, et le résultat NAC pour la piste stéréo est à 0.2 % de l'encodeur FLAC dédié.

7.9 Documents Office, PDF et gzip : recompression Deflate

Les fichiers Office modernes sont des archives ZIP de XML (docx, xlsx, pptx, odt, ods), et les fichiers PDF stockent leurs pages dans des flux Deflate (FlateDecode). Leur contenu est donc déjà compressé, et aucun archiveur ne peut beaucoup le réduire : dans le benchmark 1.1, 6.6 MB de fichiers .xlsx ne descendaient qu'à 5.6 MB avec 7-Zip. nikpak 1.2 supprime cet obstacle.

  • Détection par le contenu. Un en-tête local ZIP (PK\x03\x04) au début du fichier, %PDF- ou un en-tête gzip ; l'extension n'est jamais utilisée.
  • Décodage. Chaque flux Deflate est trouvé (entrées ZIP avec la méthode 8, flux PDF avec un en-tête zlib, chaque membre gzip) et analysé avec preflate (preflate-rs de Microsoft). preflate renvoie les données en clair plus un petit enregistrement de corrections qui décrit exactement comment l'encodeur d'origine a fait ses choix, quel que soit cet encodeur.
  • Stockage. Le fichier est stocké comme une séquence de segments bruts et de paires (clair, corrections). Le XML ou la description de page en clair entre alors dans le flux solide, où LZMA2 le compresse à une fraction de sa taille Deflate.
  • Vérification. Avant d'utiliser le résultat, nikpak reconstruit chaque flux Deflate et compare la longueur et le CRC32 de tout le fichier avec l'original. Si quelque chose diffère, ou si preflate échoue ou panique sur un fichier mal formé, le fichier est simplement stocké normalement.
  • Extraction. Les flux Deflate sont recréés bit à bit, de sorte que le .docx ou .pdf extrait est identique octet pour octet, et son CRC32 est vérifié comme pour chaque entrée.

Sur le jeu Office de la section 11.7, c'est ce qui rend nikpak plus petit que tous les autres archiveurs. Les 6.6 MB de fichiers .xlsx contiennent 71 MB de XML une fois décodés, et ce XML se compresse bien mieux que Deflate ne l'a fait. Le coût est le temps : preflate analyse environ 15 MB de données en clair par seconde. Pour cette raison, la recompression n'est utilisée qu'à -m4 et -m5, où elle est rentable (mesuré : -m3 gagnait 0.5 % pour six fois le temps). Limites : fichiers jusqu'à 512 MiB, et par flux jusqu'à 512 MiB de données en clair et 64 MiB de corrections. -mc- la désactive.

8 Chiffrement

Le chiffrement de nikpak est entièrement construit à partir de composants standard et bien étudiés (les implémentations RustCrypto d'Argon2id et de XChaCha20-Poly1305). Aucune primitive n'a été inventée pour ce projet ; le travail consiste à les combiner correctement.

8.1 Modèle de menace

La conception suppose un attaquant qui obtient le fichier d'archive et peut l'étudier et le modifier à loisir, et qui peut essayer un nombre illimité de mots de passe hors ligne. nikpak vise à garantir :

  • Confidentialité du contenu des fichiers et de tout ce qui les concerne : noms, tailles, horodatages, permissions et nombre de fichiers.
  • Intégrité et authenticité : tout changement de l'archive, que ce soit dans les données, l'en-tête, l'ordre des données ou sa longueur, est détecté avant que des données incorrectes soient acceptées.
  • Résistance aux tentatives : chaque tentative de mot de passe est rendue aussi coûteuse que possible.

Il ne masque pas le fait qu'une archive existe, ni sa taille approximative, et il ne peut pas protéger contre un logiciel malveillant sur la machine qui crée ou ouvre l'archive, ni contre un mot de passe faible.

8.2 Du mot de passe à la clé : Argon2id

Un mot de passe est une mauvaise clé : court, prévisible et tapé par un humain. Il est transformé en une clé de 256 bits avec Argon2id, le vainqueur de la Password Hashing Competition et l'algorithme normalisé dans la RFC 9106. Argon2id est délibérément à coût mémoire élevé : calculer une clé nécessite un grand bloc de mémoire qui est rempli puis relu à plusieurs reprises selon un motif dépendant des données. nikpak utilise le profil à faible mémoire de la RFC :

ParamètreValeurSignification

Voies 4Degré de parallélisme à l'intérieur d'une dérivation

Sortie32 octetsLa clé XChaCha20-Poly1305



Le coût mémoire élevé est ce qui distingue Argon2id de l'ancien PBKDF2 (utilisé par RAR5 et par le mode AES de ZIP) : PBKDF2 n'a besoin de presque aucune mémoire, de sorte qu'une carte graphique ou une puce personnalisée peut tester d'énormes nombres de tentatives en parallèle. Avec Argon2id, le matériel de l'attaquant doit fournir 64 MiB par tentative parallèle, ce qui supprime la majeure partie de cet avantage. Le coût pour l'utilisateur légitime est une fraction de seconde, payée une fois par archive.

Les paramètres sont stockés dans l'en-tête, de sorte que les versions futures pourront les augmenter sans casser les anciennes archives. À la lecture, ils sont d'abord vérifiés en plage (mémoire 8 x voies jusqu'à 1 GiB, passes de 1 à 64, voies de 1 à 64) afin qu'une archive malveillante ne puisse pas faire allouer à nikpak des quantités absurdes de mémoire avant que le mot de passe n'ait été vérifié.

8.3 XChaCha20-Poly1305 dans la construction STREAM

Les données en masse sont protégées avec XChaCha20-Poly1305, un chiffrement authentifié avec données associées (AEAD) : ChaCha20 fournit un chiffrement de flux à clé de 256 bits, la variante X étend son nonce à 192 bits (assez grand pour être choisi au hasard sans jamais se répéter), et Poly1305 ajoute une étiquette d'authentification de 128 bits à chaque message scellé. ChaCha20 est rapide sur chaque processeur sans instructions spéciales et, contrairement à l'AES à base de tables, naturellement exempt de fuites de temporisation de cache.

Une archive est bien plus grande qu'un seul message, donc nikpak utilise la construction STREAM (la même que celle des outils modernes de chiffrement de fichiers) : les données sont découpées en blocs de 64 KiB et le bloc numéro i est scellé sous le nonce

nonce (24 bytes) = random prefix (19 bytes)
| chunk counter (4 bytes, big endian)
| last-chunk flag (1 byte)



Cela donne trois garanties à la fois. Chaque bloc a un nonce unique, ce qui est essentiel pour les chiffrements de flux. Comme le compteur fait partie du nonce, réordonner ou dupliquer des blocs fait échouer l'authentification. Comme le dernier bloc porte un drapeau différent, raccourcir l'archive, même exactement à une frontière de bloc, fait échouer l'authentification : le nouveau dernier bloc a été scellé comme non final. Le préfixe de 19 octets est aléatoire par archive.

De plus, l'en-tête complet de l'archive (version, drapeaux, méthode, paramètres Argon2id, sel et préfixe de nonce) est transmis comme données associées à chaque bloc. Il est authentifié mais non chiffré ; inverser un seul de ses bits fait échouer chaque bloc. Cela bloque aussi les attaques par rétrogradation qui tenteraient d'affaiblir les paramètres stockés.

8.5 Gestion des mots de passe

  • Longueur minimale. 8 caractères lors de la création d'une archive ; les mots de passe plus courts sont refusés avec une explication.
  • Confirmation. L'invite interactive demande deux fois, n'affiche pas les caractères saisis et rejette une non-correspondance.
  • Génération. Sans mot de passe, nikpak tire 24 caractères d'un alphabet de 56 symboles qui omet les ressemblants (0/O, 1/l/I), en utilisant un échantillonnage par rejet sur le générateur aléatoire cryptographiquement sûr du système d'exploitation afin qu'aucun symbole ne soit plus probable qu'un autre. Cela fait 24 x log2(56), soit environ 139 bits d'entropie, et il est affiché une fois, dans un encadré clairement marqué.
  • Hygiène mémoire. La clé dérivée et les chaînes de mot de passe sont effacées de la mémoire lorsqu'elles ne sont plus nécessaires (la crate zeroize).
  • Canaux. Ligne de commande (-p), variable d'environnement NIKPAK_PASSWORD, invite interactive, ou stdin lorsqu'il n'y a pas de terminal. La forme en ligne de commande est pratique mais visible dans la liste des processus ; les autres formes sont préférables.

9 Résistance quantique

Les ordinateurs quantiques menacent gravement certaines cryptographies et à peine les autres. nikpak a été conçu du côté qui n'est presque pas affecté.

9.1 Ce que changent les ordinateurs quantiques

L'algorithme de Shor est le spectaculaire : il casserait tout système reposant sur les mathématiques à clé publique, c'est pourquoi les gouvernements et les organismes de normalisation migrent vers des algorithmes à clé publique post-quantiques tels que ML-KEM (FIPS 203). L'algorithme de Grover est le doux : une clé de 256 bits offre environ 128 bits de sécurité contre lui, et les itérations de Grover sont intrinsèquement séquentielles, de sorte que répartir le travail sur de nombreuses machines quantiques ne donne que la racine carrée de leur nombre en accélération.

Autrement dit, le chiffrement des données de nikpak se situe déjà à la force visée par les normes post-quantiques.

9.3 Et le mot de passe ?

L'espace de clés du chiffrement est de 256 bits, mais la clé est dérivée d'un mot de passe, donc la force réelle est la plus petite entre l'entropie du mot de passe et 256 bits. Face à un adversaire quantique, l'entropie du mot de passe est, au mieux pour l'attaquant, réduite de moitié :

Utilisez le mot de passe généré ou une longue phrase secrète aléatoire et l'archive résiste à la fois aux attaquants classiques et quantiques pour tout avenir prévisible. Argon2id aide dans les deux mondes, car le coût de chaque tentative est dominé par la mémoire, que l'algorithme de Grover ne rend pas moins chère.

9.4 « Récolter maintenant, déchiffrer plus tard »

Une menace quantique souvent citée est qu'un adversaire enregistre aujourd'hui des données chiffrées et les déchiffre lorsqu'un ordinateur quantique existera. Pour les systèmes qui échangent des clés avec RSA ou des courbes elliptiques, comme les connexions TLS ou le chiffrement des e-mails, c'est réel. Une archive nikpak n'a pas d'échange de clé : sa clé provient d'un secret qui ne quitte jamais la tête de l'utilisateur ou son gestionnaire de mots de passe. Une copie stockée ne peut être ouverte plus tard qu'en devinant ce secret, et les ordinateurs quantiques ne rendent pas cela fondamentalement plus facile.

9.5 Limites honnêtes et la route à suivre

  • « Résistant au quantique » signifie qu'aucun algorithme quantique connu ne bat la recherche générique contre ces primitives. Ce n'est pas une preuve ; la cryptanalyse de ChaCha20 et d'Argon2 continue, et le format est versionné afin que les paramètres ou les algorithmes puissent être changés.
  • Si le partage à clé publique est un jour ajouté (chiffrer une archive vers la clé d'un destinataire), il utilisera un schéma hybride, X25519 combiné à ML-KEM, de sorte qu'il reste sûr si l'un des deux composants tient.
  • La résistance quantique ne protège pas contre les erreurs d'implémentation. Voir les sections 8.6 et 10.

10 Durcissement et robustesse

Un archiveur lit des fichiers écrits par des inconnus et écrit des fichiers sur le disque de son utilisateur, ce qui en fait une cible classique. nikpak traite chaque archive comme une entrée non fiable.

10.1 Extraction sûre

  • Traversée de chemin (« zip slip »). Chaque nom d'entrée est normalisé : les barres obliques inverses deviennent des barres obliques, les composants vides et . sont supprimés, et tout composant .. entraîne l'ignorance de l'entrée avec un avertissement. Les noms absolus perdent leur racine, de sorte que /etc/passwd est extrait à l'intérieur du dossier de destination.
  • Noms Windows. Lors de l'exécution sous Windows, les composants contenant < > : " | ? * ou des caractères de contrôle, se terminant par un espace ou un point, ou égaux à un nom de périphérique réservé (CON, PRN, AUX, NUL, COM1-9, LPT1-9) sont rejetés.
  • Liens symboliques. Avant l'écriture, chaque composant existant du chemin cible sous la destination est vérifié ; un lien n'est jamais suivi. Un fichier existant est d'abord supprimé et le nouveau est créé avec create_new, qui refuse d'ouvrir un chemin existant, de sorte qu'un lien ne peut pas être utilisé pour rediriger l'écriture.
  • Bits privilégiés. Les bits setuid, setgid et collant ne sont jamais restaurés ; les permissions sont masquées aux bits rwx ordinaires.
  • Fichiers en échec. Un fichier dont le CRC32 ne correspond pas est supprimé, pas laissé derrière.

Une archive fabriquée à la main contenant ../../evil.txt, /tmp/evil.txt, ..\..\evil.txt et ok/../../evil.txt a été extraite dans les tests : rien ne s'est échappé de la destination, les entrées non sûres ont été signalées et ignorées, et un lien symbolique planté dans la destination a été refusé.

10.2 Décodeurs bornés

  • Les paramètres Argon2id sont vérifiés en plage avant toute allocation (section 8.2).
  • Les blocs chiffrés doivent avoir une longueur entre 16 octets et 64 KiB + 16 ; les noms au plus 4096 octets ; les blocs audio doivent déclarer une longueur plausible ; les régions BMP sont limitées à 256 MiB ; les codes de Rice unaires sont plafonnés.
  • Les décodeurs audio et média ont reçu des milliers d'entrées aléatoires et à bits inversés dans les tests unitaires et doivent renvoyer une erreur, jamais paniquer ni s'interrompre.
  • Le code propre de nikpak ne contient aucun bloc unsafe, et la vérification des bornes de Rust transforme toute erreur de logique qui serait un bug de corruption mémoire en C en un échec propre.

nikpak ne limite pas le taux d'expansion d'une archive, de sorte que, comme tout archiveur, une « bombe de compression » délibérément fabriquée peut remplir un disque à l'extraction. Testez d'abord les archives inconnues avec t si cela compte.

10.3 Création sûre et erreurs honnêtes

  • L'archive est écrite dans name.nik.tmp et renommée seulement lorsqu'elle est complète ; un garde-fou supprime le fichier temporaire en cas d'échec, de sorte qu'une exécution interrompue ne laisse jamais une archive à moitié écrite ou remplacée.
  • Si un fichier devient plus court pendant qu'il est archivé, nikpak s'interrompt avec un message explicite au lieu d'écrire une entrée incohérente. Les fichiers illisibles, les liens symboliques et les fichiers spéciaux sont ignorés avec un avertissement (code de sortie 1) et l'archive n'est jamais ajoutée à elle-même.
  • Les erreurs sont classées afin que les scripts puissent réagir : une erreur de somme de contrôle ou de trame à l'intérieur d'une archive est une corruption (sortie 3), un échec d'authentification est un mauvais mot de passe ou une altération (sortie 11), une écriture refusée est une erreur fatale (sortie 2).

Au niveau maximal, nikpak produit la plus petite archive des quatre outils sur chaque jeu mesuré, 2.4 à 31.7 % plus petit que 7-Zip -mx9. Le coût est la vitesse : -m5 échange du temps contre de la taille. Les chiffres ci-dessus fixent chaque outil à un cœur ; en usage réel, une archive -m5 répartit ses blocs sur les cœurs (section 4.5). Un niveau maximal plus rapide reste sur la feuille de route (section 15.2).

12.3 La résistance quantique en perspective

nikpak et RAR5 chiffrent tous deux avec une clé symétrique de 256 bits, donc tous deux sont épargnés par l'algorithme de Shor et conservent environ 128 bits de sécurité contre celui de Grover. Aucune des deux revendications ne les distingue. Ce que nikpak ajoute par-dessus est une étape de mot de passe à coût mémoire élevé (qui rend l'attaque réelle dominante, le devinement de mot de passe, bien plus coûteuse) et un chiffrement authentifié (qui rend l'altération détectable). Il a aussi été conçu dès le départ sur l'hypothèse qu'aucune primitive à clé publique ne fera jamais partie du format d'archive, et sa feuille de route s'engage sur un schéma hybride post-quantique si le partage à clé publique est ajouté.

12.4 Lequel choisir

  • Choisissez nikpak pour les archives d'audio, d'images, de musique tracker et de code source où la taille et la vitesse comptent, pour les sauvegardes scriptées, pour un chiffrement fort par défaut, et lorsqu'un format ouvert et documenté est précieux.
  • Choisissez RAR lorsque vous avez besoin d’enregistrements de récupération, de mises à jour sur place, ou que vous devez échanger des archives avec des personnes qui n’ont que des outils RAR.
  • Utilisez les deux : rien n'empêche un flux de travail d'utiliser nikpak pour les médias en masse et les sauvegardes chiffrées tout en gardant RAR pour la distribution.

12.5 Et 7-Zip et ZIP ?

La section 11.7 mesure aussi nikpak 1.2 contre 7-Zip 23.01 et Info-ZIP 3.0. En bref :

  • Choisissez nikpak -m5 pour la plus petite archive. Il est 2.4 à 31.7 % plus petit que 7-Zip -mx9 sur chaque jeu mesuré : 31.7 % sur les fichiers Office, 15.9 % sur le texte et 2.4 % sur le code source. Choisissez nikpak -m2 pour des sauvegardes rapides (56 fois plus rapide que le défaut de 7-Zip sur le code source). nikpak a aussi un chiffrement plus fort : 7-Zip utilise AES-256 avec une dérivation de clé SHA-256 qui n'est pas à coût mémoire élevé, et il ne masque les noms de fichiers qu'avec -mhe.
  • Choisissez 7-Zip lorsque le temps compte davantage au niveau maximal (il est plus rapide sur les grands jeux Office et de code source), lorsque vous avez besoin que son niveau par défaut soit petit sur les documents, ou lorsque vous devez ouvrir les nombreux formats que 7-Zip lit.
  • Choisissez ZIP uniquement pour la compatibilité. Chaque système d'exploitation l'ouvre sans logiciel supplémentaire, mais nikpak -m5 est 19.9 à 60.4 % plus petit, et le chiffrement traditionnel de ZIP est faible.

13 Compilation, déploiement et intégration

13.1 Windows avec PowerShell

nikpak est écrit en Rust et compilé avec Cargo. Sous Windows, Rust a besoin d'un éditeur de liens C/C++, fourni par les Visual Studio Build Tools. Dans un PowerShell administrateur, installez les deux une fois puis rouvrez PowerShell :

winget install Rustlang.Rustup
$o = '--wait --passive --add Microsoft.VisualStudio.Workload.VCTools'
$o += ' --includeRecommended'
winget install Microsoft.VisualStudio.2022.BuildTools --override $o



Si winget n'est pas disponible, installez Rust depuis rustup.rs et les Build Tools for Visual Studio avec la charge de travail Développement de bureau en C++. Ensuite, dans le dossier qui contient les sources :

.\build.ps1 # builds dist\nikpak.exe and dist\unNik.exe
.\build.ps1 -Test # runs the unit tests first


# if PowerShell refuses to run scripts:
powershell -ExecutionPolicy Bypass -File .\build.ps1



build.ps1 vérifie que Cargo est installé (et indique comment l'installer sinon), lance la compilation, explique la cause habituelle en cas d'échec, et copie l'exécutable vers dist\nikpak.exe.

L'installateur Windows

.\build.ps1 -Installer (ou npm run installer) compile aussi le programme d'installation dist\nikpak--setup.exe avec Inno Setup 6.3 ou plus récent (installez-le une fois avec winget install JRSoftware.InnoSetup). Le script est installer\nikpak.iss ; la version est prise dans Cargo.toml. C'est ce fichier d'installation qui est mis en ligne sur les sites de shareware et de téléchargement.

  • Par défaut, il installe uniquement pour l'utilisateur courant, sans droits d'administrateur ni invite UAC, dans %LOCALAPPDATA%\Programs\NikPak. Sa première page propose « installer pour tous les utilisateurs » (Program Files, nécessite des droits d'administrateur).
  • Il affiche LICENSE.txt pour acceptation et installe nikpak.exe, unNik.exe, les icônes, LICENSE.txt, THIRD-PARTY-NOTICES.txt et CHANGELOG.md. Il ajoute une entrée au menu Démarrer, une icône de bureau optionnelle et, sur demande, le dossier au PATH pour la ligne de commande. Il enregistre un désinstalleur dans Paramètres > Applications.
  • Raccourcis : NikPak, unNik et la licence dans le menu Démarrer ; NikPak sur le bureau (toujours) et unNik sur le bureau en option.
  • Les fichiers .nik sont toujours enregistrés (depuis la 1.5.2) : ils reçoivent leur propre icône (nikfile.ico, une page avec une fermeture éclair, comme les fichiers .zip), le nom de type « NikPak archive », et un double-clic les ouvre dans unNik (« Ouvrir avec unNik » dans le menu contextuel). unNik est aussi listé dans « Ouvrir avec » et dans Applications par défaut. Le désinstalleur retire l'enregistrement. Si les fichiers .nik étaient déjà configurés pour s'ouvrir avec un autre programme, Windows conserve ce choix jusqu'à ce qu'unNik soit choisi une fois dans « Ouvrir avec ».
  • Le dernier « Lancer NikPak » démarre NikPak en tant qu'utilisateur normal, jamais en tant qu'administrateur, afin que le glisser-déposer fonctionne. Les mises à jour s'installent par-dessus la version précédente (AppId fixe). La licence dans %APPDATA%\nikpak est conservée lors de la mise à jour et de la désinstallation. Le programme d'installation ne contient jamais de clés ni de fichiers de clés.
  • L'installateur s'exécute en anglais ou en français, selon Windows. Avant la publication, signez nikpak.exe et le programme d'installation avec un certificat de signature de code, afin que Windows SmartScreen n'avertisse pas d'un éditeur inconnu.

buildall.ps1 compile tout ce qui est publié en une seule passe — nikpak.exe, unNik.exe, les deux programmes d'installation et SHA256SUMS.txt — les copie dans binaries\, reconstruit le site web et le met en ligne par FTP (-NoUpload saute la mise en ligne). Le second programme d'installation, unnik--setup.exe (installer\unnik.iss), installe unNik seul, l'explorateur d'archives gratuit ; lorsque NikPak est déjà installé, il n'installe que le programme, de sorte que les menus ne se doublent jamais.

13.2 Compilation avec npm

Les projets Rust n'utilisent pas npm, donc npm n'est jamais requis. Pour plus de commodité, le projet contient un petit package.json dont les scripts appellent simplement Cargo, afin qu'un développeur habitué à un flux Node.js puisse taper des commandes familières :

13.3 Un exécutable autonome

Le fichier .cargo/config.toml lie statiquement le runtime C pour les cibles Windows MSVC. Le nikpak.exe résultant (plusieurs MB avec l'interface graphique, environ 2.3 MB sans) n'a donc aucune dépendance DLL et n'a pas besoin du Visual C++ Redistributable sur les machines où il s'exécute. Le profil release active l'optimisation complète, l'optimisation à l'édition de liens, une unité de génération de code unique, la suppression des symboles et panic = abort pour un binaire petit et rapide.

13.6 Scripts

Des codes de sortie prévisibles et le mot de passe par variable d'environnement rendent nikpak facile à scripter. Une sauvegarde PowerShell qui considère les avertissements comme acceptables et tout ce qui est pire comme un échec :

$archive = "D:\Backups\docs-$(Get-Date -Format yyyy-MM-dd).nik"
# the password comes from a file or secret store, not from the script
$env:NIKPAK_PASSWORD = Get-Content "$env:USERPROFILE\.nikpak-secret"


nikpak a -p -m3 -inul $archive "$env:USERPROFILE\Documents"
if ($LASTEXITCODE -gt 1) { throw "nikpak failed: $LASTEXITCODE" }


nikpak t -inul $archive # verify what was written
if ($LASTEXITCODE -ne 0) { throw "archive verification failed" }



La même chose dans un script shell, en utilisant la commande de liste brute pour alimenter d'autres outils :

export NIKPAK_PASSWORD="$(cat ~/.nikpak-secret)"
nikpak a -p -m3 -inul "backup-$(date +%F).nik" ~/Documents || [ $? -eq 1 ]
nikpak lb backup-2026-10-16.nik | grep -i '\.wav$'

14.2 Tests de bout en bout

  • Chaque archive de benchmark a été extraite et comparée à sa source, octet pour octet (SHA-256 pour le jeu de 10 949 fichiers), à plusieurs niveaux.
  • Une archive mixte (WAV, MOD, BMP, texte, données aléatoires, sous-dossiers) a été créée, listée, testée, extraite complètement, et un seul fichier a été extrait de son milieu.
  • La même archive a été créée avec chiffrement, testée avec le bon et le mauvais mot de passe, puis extraite.
  • Les archives écrites par la version de format précédente (1.0) ont été ouvertes par la 1.1.
  • La saisie interactive du mot de passe a été exercée via un pseudo-terminal : mots de passe correspondants, une non-correspondance, une saisie vide (génération), bons et mauvais mots de passe à l'ouverture.

14.3 Tests d'attaque

L'altération, la troncature, le réordonnancement de blocs, la manipulation d'en-tête, les fichiers poubelle et les archives à traversée de chemin de la section 10.1 ont été exécutés contre chaque version candidate. Les résultats sont tabulés dans les sections 8.6 et 10.1 ; le résultat attendu dans chaque cas est un refus, un message clair et un code de sortie non nul, jamais une panique et jamais une écriture hors de la destination.

14.4 Défauts trouvés par les tests

La campagne de tests est la raison pour laquelle plusieurs défauts n'existent pas dans le programme publié. Deux exemples : une recherche de paramètre de Rice qui échouait pour l'audio 32 bits et aurait écrit un code de plusieurs gigaoctets (trouvée par la matrice de tests unitaires et corrigée), et un échec de somme de contrôle zstd qui était signalé avec le code de sortie générique 2 au lieu de 3 (trouvé dans les tests d'altération et corrigé). Un troisième exemple est la méthodologie de benchmark elle-même : la première comparaison avec RAR utilisait son défaut non solide, ce qui flattait nikpak sur le code source ; elle a été refaite en mode solide, et les résultats du chapitre 11 sont les corrigés.
